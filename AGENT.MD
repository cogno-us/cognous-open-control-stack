## 2. Anti-drift architecture rules

1. **One controlling plan.** Current static program/contract/sprint plan and canonical decision records control; conversations are disposable context. No requirements introduced by conversational accumulation.
2. **Contract before code (CA03).** Identify exact source, affected external reliance boundary, acceptance and competent change authority. Freeze a shared boundary before parallel migration. Reopen only with a source-backed compatibility decision.
3. **Reuse before build (CA01).** Inspect existing qualified modules, adapters, fixtures, controls and evidence before adding another. Avoid duplicate capabilities and dashboards.
4. **Smallest complete scope (CA02).** No speculative abstractions, future-proofing, redundant compatibility layers, unused configuration, or hypothetical requirement. Remove obsolete internal complexity where safe; honor actual external contracts (CA12/CA21).
5. **One canonical writer.** Parallelize independent pinned modules, discovery and fixtures; serialize shared contracts, authoritative state, schemas, admission logic and integration (CA09). More agents are useful only when their work is genuinely independent and ready.
6. **Finish authorized work.** A draft PR is not a delivered capability. Continue through focused fixes, eligible review, checks and permitted merge/handoff (CA10); never infer merge/release approval from implementation authorization.
7. **No gratuitous constitutional changes.** Project rules and proposed addenda are binding only to the extent duly adopted. No silent policy broadening or weakening of protected invariants (CA18).

## 3. Governance without bureaucracy

- Escalate **only genuine reserved decisions**: architecture/contract changes, material external compatibility, security exceptions, unverified authority, changed qualification rules/oracles, paid work beyond cap, irreversible effects, required independence, certification, release, or deployment.
- An existing bounded authorization should cover routine implementation, repairs, focused tests and permitted completion. Do not re-request approval at each step or introduce redundant provenance ceremonies. Still verify authorization once at the relevant protected boundary and retain its identity.
- Resolve ordinary test, CI, packaging, link and tooling failures autonomously within scope; when blocked, issue **one** actionable decision with exact evidence, alternatives, consequence and recommended next action. Continue unaffected work.
- Use existing GitHub issue/project infrastructure as the control panel. Prefer **issues** for program plans, contract proposals/decisions and sprint tracking where that avoids documentation-only CI. Use PRs for actual versioned repository artifacts/code and changes that require review/merge. An issue edit does not itself canonize an adopted contract.
- Fix trivial defects on the existing PR when practical instead of creating PR chains. Do not create duplicate status ledgers, issue templates, approval gates, or report volumes without a specific requirement.
- One fresh lead-builder session per sprint; short-lived task-specific workers. Continuity resides in static plan, GitHub issues/PRs, decision and sprint-status records.

## 4. Testing and CI: minimum falsifiable evidence

Classify testing by **highest reachable consequence**, including transitive consumers/configuration changes, not by changed line count or task archetype. These T-tiers are distinct from constitutional review Tiers 1–3.

| Tier | Default evidence |
| --- | --- |
| **T0** — nonsemantic editorial | Inspect scope; links/content/format consistency. No automatic full regression. Governing contract changes are not T0 merely because they are prose. |
| **T1** — isolated low consequence | Focused unit and relevant positive, negative, boundary/error checks. |
| **T2** — interfaces/composition | Exact schema/contract, affected consumers, integration and negative tests. |
| **T3** — authority, security, persistence, effects, canonical state | Broad **affected-path** regression, critical negative/adversarial, failure, recovery and security coverage. Not automatically every unrelated repository test. |
| **T4** — frozen acceptance milestone | Full **prescribed applicable** independent campaign at exact pinned subject, configuration and oracle. |

Default cadence: (1) small iterative developer checks; (2) affected PR/sprint integration and mandatory checks; (3) prescribed independent qualification at deliberate frozen milestones. Pick the **smallest test suite that can falsify the material claim**, without compromising mandatory controls. Keep expensive full campaigns, provider calls and production effects OFF unless explicitly authorized.

Use path-sensitive CI only where allowed and safe; preserve protected required checks and cover workflow/filter/rename/generated-artifact bypass risks. For changes to CI selectors, analyze altered reachability. An inapplicable suite is **SKIPPED BY SCOPE / N/A**, not PASS. Do not run duplicate workflows or independent campaigns merely because another PR opened.

Before rerunning historical tests, establish **why** the tested behavior, dependency or environment is newly reachable or changed. Preserve original historical evidence, failures and negatives, but separate it from active regression requirements. Retire obsolete test machinery only after confirming no adopted obligation or supported behavior depends on it. Reuse prior PASS only with exact-source/config/dependency/consumer applicability; no false transfer across revisions (CA06–CA08).

Independent oracle and qualification remain separate from builder-controlled developer checks when required. Never edit a frozen oracle to match candidate output, conceal adverse results, label a skip PASS, or infer real-world custody from emulator success.

## 5. Builder instructions and orchestration

When giving the user instructions to send to a builder, output **one self-contained code block only**. Begin exactly:

`Put the maximum number of parallel agents to work within authorized, nonconflicting scopes.`

Use the Constitution's eight fields **in order**: **Identity, Authority, Ownership, Inputs, Acceptance, Delivery, Boundaries, Governance**. Keep content concise but executable. Include:

- Actual repository, source/branch pin, controlling static plan, adopted Engineering Constitution revision (or explicit verification prerequisite), and immutable contract references.
- One primary task archetype: A architecture/contract; B scoped implementation; C defect/CI repair; D independent qualification. Specify the role separately.
- Authorized outputs and actions, one canonical writer, disjoint workers, protected paths, external-effect and financial limits.
- T-tier independently assessed from reachability; falsifiable positive/negative acceptance; reuse rationale; mandated checks; limits of independent qualification.
- Exact-head deliverables, evidence, failure handling, rollback/compatibility and stop/escalation boundaries.
- Applicable EP/CA source-backed bindings; where exact adopted article text is required, use verbatim canonical Required behavior and Prohibited shortcut with task-specific binding. Do not invent SHAs, paths, adoption, existing tests, authority, or grants.

Use maximum **useful** parallelism, not an arbitrary agent count. Do not dispatch competing canonical writers. Before a batch migration, inventory eligible inputs and freeze shared schema/evaluator once. Routine corrections proceed without repeated operator questions; reserved decisions are escalated precisely once.

## 6. Evidence, claims and delivery stages

Preserve causal and decision lineage: original failures, rejected alternatives when material, exact sources, environment/config pins, and supersession. Distinguish **PROPOSED, DOCUMENTED, IMPLEMENTED, DEVELOPER-TESTED, INDEPENDENTLY QUALIFIED, INTEGRATED, DEPLOYED, PRODUCTION-QUALIFIED**. Evidence verdicts: **PASS, FAIL, BLOCKED, NOT EXECUTED, evidenced N/A**. No stage implies the next (CA16/CA19/CA23).

Prior to an authorized merge, verify actual current head, required applicable CI, reviews, compatibility, independent obligations, approval authority and migration/rollback; verify actual merged identity afterward. No PR-count or green-check count is a quality metric.

Measure actual accepted functionality, authorization-to-independent acceptance, rework, unnecessary CI/test executions, latency, operational burden and cost per accepted deliverable. If only a projection is available, label it an estimate (CA08/CA13).

## 7. OCS-specific priorities

1. **Reconcile execution baseline:** current OCS plan, contracts, open issues/PRs, qualification status and constitutional adoption. Close duplicated/superseded work without erasing history.
2. **Rationalize CI and historical tests:** inventory mandatory versus redundant suites; establish safe scope filters and evidence reuse; remove unnecessary repeated execution, not safety obligations.
3. **Simplify internal architecture:** inspect adapters, old compatibility branches, abstractions and duplicated governance machinery; remove only with verified impact and appropriate contract transitions.
4. **Preserve domain boundaries:** knowledge/evidence, authenticated provenance, legitimate authority, effect execution, authoritative observation and independent verification are distinct. Do not import proprietary ISS/private methodology into public OCS without authorized public contracts.
