# Step 1.4 contract draft: independent evidence handoff

**Proposed contract draft, documentation only.** No decision is recorded; ADR-P01 and ADR-P05 are used as labeled proposed assumptions. No locked component is changed, no Qualification criterion is edited, and nothing here selects a pin, a release or an effect. Release and production remain on HOLD.

Static reading only; nothing was executed. Read at: Orchestrator `a745e131` (`development/acceptance/o6-q5/candidate.json` and `admission.py`), Qualification `main` (`suites/_pins.py` and the retained refreeze log, read through the repository API), hub `component-lock.json`.

## 1. Rules fixed by the controller's answers

- **The handoff adds evidence only in v0.2.** It does not replace Qualification-controlled refreeze authorship and does not select component pins, automatically or otherwise.
- **Qualification consumes or does not consume the handoff by its own decision.** Engineering delivers the producer side and a documented interface; any ingestion job, expectation or suite is Qualification's.
- **One canonical profile owner.** Digests in the envelope use the canonical profile frozen at step 1.3 (ADR-P01); this contract does not define a second one.

## 3. The Qualification side (what the handoff must not displace)

Qualification resolves pins as the freeze manifest (never edited) overridden by refreeze-log entries applied in file order, each requiring its `from_sha` to equal the pin in force (`RefreezeError` otherwise); only entries whose status is APPLIED or APPLIED-IN-WORKFLOW take effect (`suites/_pins.py`). Each retained entry carries an id, a named human authorization with date and quotation, component, repository, `from_sha`, `to_sha`, reason, behavior changes, open item, historical results at the old pin and status (for example RF-1). Pin selection in Qualification is therefore a recorded human-authorized act. The handoff is evidence about a candidate; it is not that act.

## 4. Proposed envelope (conceptual; names frozen at the M0 gate)

| Field | Content | Written by |
|---|---|---|
| `profile`, `schema_version` | Envelope identity | Producer |
| `canonical_profile`, `digest` | Profile name and digest of the envelope body (step 1.3 profile) | Producer, once; envelope is then immutable |
| `producer` | Producing component and its exact revision | Producer |
| `hub` | Hub repository and exact source sha the tuple was read from | Producer |
| `tuple` | For each component: repository, exact sha, interface versions, as read from a lock supplied as input; plus the lock digest | Producer, read-only from the lock |
| `evidence` | List of engineering evidence entries: kind, producing commit, run id, result digest, retained raw artifact references | Producer |
| `claim_scope` | The narrow claim the evidence supports and its exclusions | Producer |
| `intent`, `effects`, `release_selection`, `operational_trust` | Fixed values: read-only candidate evidence, effects disabled, selection unchanged, operational trust not established unless independent operator evidence is attached | Producer; invariant |
| `predecessor` | Digest of the envelope this one supersedes | Producer |
| Qualification reference | Empty at creation; only Qualification may record its own result elsewhere in its own records | Never the producer |

The envelope has no field for a verdict, an expectation, a pass or a pin choice. A producer cannot write one, and a consumer must not read any field as one. Supersession is by a new envelope with a new digest; an issued envelope is never edited.

## 5. Lock-driven intake (design; mechanics built at step 3.1)

- A lock-driven profile reads component revisions from a hub `component-lock.json` supplied to the run and bound by the lock digest, instead of constants. The existing `o6-q5` constants stay as the historical profile they are; they are not rewritten (PD-A04).
- Lock key shapes differ (for example `moltbot_safe` uses `accepted_sha` while most entries use `sha`; PD-L08), so intake normalizes keys through one documented mapping and fails closed on an unknown shape.
- Intake refuses an envelope whose tuple differs from the supplied lock, whose lock digest does not match, or whose fixed fields are changed; it never edits the lock and never writes a pin.
- No historical pass transfers: an envelope for tuple T carries only evidence produced at T, and its claim scope says so (F-08 in [1.2](1.2-authority-and-separation.md)).
