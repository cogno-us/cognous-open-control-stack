## 1. Partitions (restated from the adopted direction)

1. **Constitutional floor, in code**, one gate per component. A registry entry cannot disable or weaken any floor item: mandatory applicability, separation of authorization and evidence, deterministic completeness, fixed precedence among adverse results, preservation of all established adverse causes, no allow without all necessary check evidence, no model-origin authorization, source and negative-record integrity, no shortcut from a governance result to an external effect.
2. **Versioned, authenticated registry, as data**: check ids and versions, applicable classes and profiles, required or advisory status, conditional applicability predicates, evaluator ids and versions, typed input contracts, failure dispositions, reason-code mappings, scanner term lists and tables, negation scopes, allow-listed excusals, rule-set identity.
3. **Registered evaluators, as code**: pure, deterministic, separately qualified, with stable ids and versions; no expressions, scripts or caller-supplied rules.

## 4. Authentication: what exists and what is claimed

The existing `rule-revision/0.1` record (Control Plane `rule_revision.py`) states its own limits: the signer is an asserted name, the store is a plain JSON file without keyed integrity, and it provides visibility to an honest reader rather than tamper evidence. R0 therefore does not treat it as authentication.

Proposed bootstrap (ADR-P03, hub-owned immutable artifact): provenance is established by a digest the Control Plane is configured with, held outside the store, inside an explicitly versioned reference profile, as the adopted direction permits. No settings file grants a bootstrap exemption, and authentication establishes provenance, not constitutional validity: the gate validates the registry against its floor before activation. A keyed signature profile is a later, separately qualified step. The claim for v0.2 is "pinned and immutable", not "signed".

## 5. Activation, freshness and refusal rules

A registry becomes active only through the Control Plane's own gate. It is refused, leaving no active rule set and the previous behavior unchanged, when any of these holds:

- schema invalid, unknown member, wrong type, null or non-boolean in a typed position;
- digest does not match the configured pin, or the canonical profile is unknown;
- a mandatory check is absent, marked advisory or marked not-applicable without a proven source predicate;
- a rule is duplicated or shadowed by a conflicting rule;
- an evaluator id or version is unknown or has no qualification reference;
- the epoch is not strictly greater than the active epoch (no downgrade);
- the predecessor reference does not match the active record.

The resolver derives the total mandatory manifest by deterministic lookup from the authenticated policy version, class, profile and assurance level, and never falls back to a smaller manifest. Publication is not activation; an unacknowledged publication reads UNKNOWN, not ACTIVE (CA-03). Offline restart uses the last activated record only within a declared age bound; otherwise it holds. Historical re-evaluation uses the original registry bytes; current-policy re-evaluation is a separate event and never relabels an old verdict.

## 8. M1 family evaluation (select neither; recommendation only)

Criteria: exists in current source; bounded for exhaustive reconciliation; does not move the code floor; has an independent oracle that can be frozen before the candidate; needs no locked-component change, or states which; is complete as a family or states its exclusions.

| Criterion | Scanner rules and tables | Mandatory-check catalogue |
|---|---|---|
| Exists and bounded | Yes: three measured copies, 85 distinct lookalike keys, 4 named rules in two copies | Yes, but the Control Plane side is a procedural region of about 369 lines with no table |
| Floor stays in code | Yes (scanners are accident-prevention lint, not a security boundary) | Floor is the content; only data and evaluator references can move |
| Independent oracle freezable first | Yes: a corpus of inputs can be frozen and each key and rule accounted for | Harder: equivalence over decision outcomes across profiles |
| Locked-component change | Only if the verifier copy is migrated (the verifier is locked) | Likely yes: resolver and rule kind in the Control Plane |
| Complete as a family | Complete across the stack only if the verifier is migrated | Complete only for the data portion |
| Adopted sequence | "Scanners come first: smallest and most frequently bypassed" | Follows the scanners |
| Needs operator approval | Yes if the normative behavior differs from any copy (ADR-P02) | Yes for any changed gate behavior |

**Recommendation (preliminary; for the M0 gate, not a selection).** The smallest complete, independently testable family is the claim and wording scanner family, scoped for M1 to its two unlocked consumers (hub and ergonomics), with the locked verifier copy named as an explicit exclusion and scheduled for M2 as an F3 change. This keeps M1 free of locked-component changes. The cost is that the family is complete only as far as its exclusion statement says; the claim text must carry that. If the gate prefers a family that also covers the verifier, the M1 estimate gains an F3 cascade. The estimate in [../estimates-m0-m1-m2.md](../estimates-m0-m1-m2.md) assumed part of both families (conservative) and is not revised here.
