# Step 1.2 contract draft: authority and separation

**Proposed contract draft, documentation only.** It records no operator decision, adopts no ADR, changes no locked component, and edits no Qualification expectation or verdict logic. Release and production remain on HOLD. ADR-P01 to P09 ([../adr-proposals.md](../adr-proposals.md)) are used here as labeled proposed assumptions. Status of every normative sentence below: PROPOSED until the M0 gate (operator review) records an outcome in a versioned successor document.

Static reading only. Sources read at: Orchestrator `a745e131` (`ARCHITECTURE.md`, `CONTRACTS.md`, `AGENTS.md`, `orchestration/`), Control Plane `0a41faa9`, Execution Runtime `ec728da6`, Qualification `main` (`suites/_pins.py`, retained refreeze log), the hub registry document, and the owner's paper "From Mainline to Governed Cognition" (August 2026; conceptual, no empirical test). Nothing was executed.

## 1. Principle

Generating a possibility is broad; imposing it on shared state is narrow. Every component below has one kind of standing, and no component acquires another's standing by capability, retry, record validity, orchestration assignment or identity. The paper's accountable-certification and scoped-authority principles supply the vocabulary; the existing component boundaries supply the content.

## 2. Exclusive powers

| Party | Exclusive power | Never |
|---|---|---|
| Action Manifest | Declares actions and effects | Grants authority |
| Control Plane | The single decision gate: effective authorization at effect time; rule-set and evaluator use inside its gate | Delegates the gate; accepts a rule set without validating it against the floor |
| Execution Runtime | Constrained execution under an authorized envelope; attempt recording | Authorizes, widens a grant, treats acknowledgement as verification |
| Orchestrator | Workflow coordination: assignment, sequencing, durable workflow state, recovery by reconciliation | Mints or widens grants, adds a permission, issues a verdict, certifies its own outcome, bypasses a component control, retries after unknown |
| Qualification | Frozen expectations, independent oracles and verdicts; control of its own refreeze log | Executes producer code as its own acceptance; accepts a producer-written expectation |
| Hub | Selection of component-lock identity; contract and release documentation | Auto-advances a pin; treats a document as a qualification |
| Registry (data) | Carries versioned rule data and evaluator references | Disables or weakens the constitutional floor, which stays in code |
| Replay, Evidence Pack, ODES | Reconstruct and project recorded evidence | Re-authorize, infer approval, or prove an effect was independently verified |
| Operator | Adoption of ADRs and the M0 gate; release and deployment decisions; repository settings | (reserved; nothing here transfers it) |

Basis: Orchestrator `ARCHITECTURE.md` ("Authorization is not execution; executor ACK is not independent observation. Replay and evidence reconstruct what was recorded and cannot re-authorize actions. Workflow coordination must not bypass these component-level controls.") and `CONTRACTS.md` items 3 to 7. The contract restates and tightens these; it adds no new power.

## 4. Promotion-boundary table (CA-06; PD-C05)

A promotion makes something canonical or externally relied on. The table records the authority and evidence, not a new authority. "Reversible" follows the existing reversibility modelling (Control Plane `reversibility.py`, ODES `effect-reversibility`), which this contract does not redefine.

| Artifact class | Promoting authority | Required evidence | Reversible? |
|---|---|---|---|
| Component pin in `component-lock.json` | Operator through the hub | Qualification verdict on the exact tuple; refreeze-log entry with a named human authorization | Yes, by a new lock revision; history is kept |
| Registry artifact publication | Hub (digest pin) | Registry validation against the floor | Yes; publication is not activation |
| Rule-set activation | Control Plane within its gate, at an epoch | Valid schema, qualified evaluators, no shadowing, monotone epoch | Yes by a higher epoch; old records keep original identity |
| Qualification verdict | Qualification | Frozen expectations and raw observations | Superseded by a new run with a new identity, never edited |
| Orchestrator workflow state | Orchestrator | Its own transition record | Yes; workflow states are internal |
| Effect commit | Control Plane and Runtime | Valid grant, authorized decision | No; compensation needs new authority |
| ADR adoption, M0 gate | Operator | Versioned decision document | By a successor document |
| Release or deployment | Operator | HOLD lifted by a separate act | Not applicable in v0.2 |

Boundary commitment rule (paper 5.5; no-regressions): a change to a committed field is opt-in or declares a new profile identifier; old records re-verify byte-identically under new code. Surface comparison extends to the new objects at step 4.1.

## 5. Orchestrator–Qualification ownership and migration

Three separate changes (see [../ownership-and-sequencing.md](../ownership-and-sequencing.md)): A migrate engineering integration responsibility, B retain independent oracles in Qualification, C add operational coordination. Handoff first, coordination second.

**What S01 and this reading establish.** The refund chain exists three times (Orchestrator `development/scenarios/customer_refunds`, Qualification matched-refund and `suites/v1-scenarios`, hub reference profiles). The Orchestrator's candidate admission is hardcoded to an older tuple (see [1.4](1.4-evidence-handoff.md)); it does not read the selected tuple.

**Proposed v0.2 migration scope (direction from the orchestrator controller).** One bounded customer-refund scenario's engineering assembly becomes the Orchestrator's canonical executable scenario. Historical scenarios in all repositories are preserved unchanged as history. Qualification keeps its independent matched-refund expectations; nothing is deleted or copied. The canonical engineering chain is the Orchestrator's, re-pinned to the selected tuple through a lock-driven profile (step 3.1), not by rewriting O5 or O6 history.

**Qualification's side is Qualification's decision.** Whether and how Qualification consumes an Orchestrator-produced candidate (an ingestion job, a changed expectation, a new suite) is its own controller work. Engineering delivers the producer side and a documented interface only.

## 6. Path-ownership proposals (ADR-P06; no settings change)

Protect only paths that carry a trust boundary. Exact lists are confirmed with each repository's owner; the classes below come from the sources read.

| Repository | Candidate protected path classes |
|---|---|
| Qualification | Controller and verdict logic (`tools/v1_validation.py`); frozen expectations and requirement inventories; suites that serve as oracles; pin engine inputs (`suites/_pins.py`, freeze manifest, refreeze log); comparator digests |
| Hub | `component-lock.json`; release-selection and release-status documents; qualification-surface contracts |
| Orchestrator | None proposed as separate trust boundary; engineering code is reviewed under the normal risk-proportionate policy |

Repository settings (CODEOWNERS, required reviews, rulesets) are changed only by the operator. S01 recorded no CODEOWNERS and zero required approvals with admin bypass in the Orchestrator and Qualification repositories (PD-A05).
