## 1. What step 2.4 is, in the register's words

[engineering-register.json](../engineering-register.json), step `2.4`, title "Activation, rollback and freshness", phase P2, sprint S05, tier 3, `dependencies`: `1.3`, `2.3`; `planning_disposition`: `PROPOSED`; `s01_defects`: `PD-B05`, `PD-H02`; effort person-days I 5/8/14, T 3/5/8, Q 3/5/8.

- `acceptance` and `exit_criteria`: "authenticated selected epoch reusing existing commit-bound mechanisms; local active-rule-set acknowledgement and mismatch detection".
- `estimate_basis`: "S01 preliminary, confidence LOW: Extend runtime policy row with digest and epoch, reuse custody epoch and generation fence; local comparator; touches locked runtime and Control Plane (F3 requalification not included). See s01/estimates.md for assumptions."
- `stop_condition`: "Unresolved mandatory source, bypass, unsupported claim or authority conflict; halt affected path".

"F3" wording in the programme: a locked-component change needs "F3 requalification, refreeze and re-review before acceptance" ([f3-change-proposals.md](../s02/f3-change-proposals.md), preamble) and is never covered by this register's estimate. The cost observed for one refreeze is seven PRs in seven repositories (PD-C01 in [s01/defects.md](../s01/defects.md), line 20). The planning contingency (assumed, not measured) is M1 10/31/76 and M2 8/23/64 person-days ([estimates-m0-m1-m2.md](../s02/estimates-m0-m1-m2.md), "Refreeze and requalification contingency"), outside the register's 2.4 figures.

What 1.3 section 5 says activation is (summarized from [1.3 R0](../s02/contracts/1.3-registry-r0.md)): a registry becomes active only through the Control Plane's own gate; it is refused, leaving no active rule set, on schema fault, digest not matching the configured pin, unknown canonical profile, mandatory check absent/advisory/not-applicable without a proven source predicate, duplicate or shadowed rule, unknown or unqualified evaluator, epoch not strictly greater than the active epoch, or a predecessor that does not match the active record. The resolver derives the total mandatory manifest by deterministic lookup from the authenticated policy version, class, profile and assurance level and never falls back to a smaller manifest. Publication is not activation: an unacknowledged publication reads UNKNOWN, not ACTIVE. Offline restart uses the last activated record only within a declared age bound, otherwise it holds. Historical re-evaluation uses the original registry bytes.

## 5. Proposed design options (none selected; none authorized)

Common design constraints (from 1.3 and Q13): publication is not activation; a mandatory manifest comes from a deterministic lookup and never falls back to a smaller one; epochs strictly increase and rollback is by a higher epoch (never a downgrade); activation happens only through the component's own gate, which validates against its floor; evaluator id and version are matched exactly (Q2); inapplicability is a typed, justified disposition (Q3); the claim is "pinned and immutable", not "signed".

### Option A. Hub-local reference activation (no locked change)

Add to `tools/` a reference model of "selected epoch, local acknowledgement, mismatch detection" that works on `RegistryStore` records: an explicit active pointer held outside the store, activation only after `validate_record` and `check_completeness`, strictly increasing epoch via `check_succession`, UNKNOWN until acknowledged, an age bound that makes offline restart hold.

- Gains: deterministic, testable, no F3, can be independently qualified as a mechanism (level 1 of 1.3 section 7).
- Risks: it is a model, not the gate; no decision is bound to the active rule set, so register acceptance ("reusing existing commit-bound mechanisms") is not met; it can be misread as real activation, so naming and claim text must say reference model only; the pointer held outside the store is itself a custody question (compare Q10) and must have a named owner.
- Needs from the operator: whether a reference-only 2.4 satisfies the programme's intent, or is only a stepping stone.

### Option B. Opt-in decision-context binding (FP-04 minimum)

The Control Plane carries an opt-in context member holding the active rule-set `{profile, digest}`, the exact evaluator ids and versions and the epoch, and its gate refuses activation per the 1.3 section 5 list. With the member unset, bytes are identical to today.

- Gains: the first point where a decision can be tied to a rule set; limited to one locked component (plus ODES contract text if the kind literal or a new contract member is added).
- Risks: F3 requalification and at least one refreeze cascade; the verifier has no evaluator version member, so exact evaluator matching needs a mapping decision; adding a kind to the `RuleKind` literal changes a locked contract; the opt-in member must be proven byte-neutral when unset.
- Needs from the operator: the F3 authorization for the Control Plane (and ODES if touched); which package is first.

### Option C. Register 2.4 as written

Option B plus the runtime in-transaction policy comparison (`authority_policies_v1` gains digest and epoch), the generation fence and digest custody epoch reused for freshness.

- Gains: matches the register's acceptance wording (commit-bound, local acknowledgement and mismatch detection); strongest freshness story.
- Risks: largest blast radius (five to six locked components, a multi-component refreeze); the runtime path touches the effect-adjacent surface, so FP-01 effect-surface closure interacts (the runtime must stay synthetic SQLite); epoch sharing across the exchange fence and BitRep custody creates a cross-component custody commitment that the architect ruling says to escalate (new external custody commitments); the register's own figures exclude F3.
- Needs from the operator: separate F3 authorization per touched component, and an ownership decision for the epoch authority.

### Option D. Stage A then B (a sequencing, not a fourth mechanism)

Build A first (unlocked, qualifiable), carry its qualified semantics into B as the specification of what the gate must do, and keep C for a later decision. The risk is that A and B diverge; the mitigation is that Qualification freezes the A negative controls before B exists (1.3 section 7), and B must satisfy the same controls.

### Rollback and freshness (all options)

Rollback is "by a higher epoch" ([FP-04](../s02/f3-change-proposals.md)): a new record with a strictly greater epoch whose predecessor is the active digest, never a lower epoch. Freshness is the declared age bound for offline restart; its numeric value is an owner decision and is not proposed here. UNKNOWN versus ACTIVE: an unacknowledged publication is UNKNOWN.
