## 1. Q8: root ancestors and the restricted qualification profile

### 1.1 Current behavior (reading)

The source-preserving handoff reader checks only the final component of the root for being a symlink. Ancestors of the root are resolved by the operating system and are not detected. The record discloses this with two fixed members: `preservation.symlinks_followed: false` holds only for components below the root, and `preservation.root_ancestors_resolved_by_os: true` states that the root's ancestors were resolved by the operating system (README "Stated limits", third bullet; `preserve.py:59` and the docstring at `preserve.py:211`). Both are fixed fields; changing either is refused as `fixed_field_changed` (README; `tests/.../test_preserve.py::test_root_ancestors_flag_cannot_change`).

### 1.2 Decision (Q8, APPROVE disclosure with qualification enforcement)

1. General handoff record: `root_ancestors_resolved_by_os` is preserved. The record stays truthful about what the general reader does. No universal refusal of ancestor symlinks is introduced, because some supported environments legitimately use them (for example a checkout reached through a symlinked mount or home directory).
2. Restricted qualification profile: it must not rely on the general record's disclosure. It requires a verified root and ancestor-chain policy appropriate to the environment (section 1.3).
3. Disclosure alone is not isolation. A record that says "ancestors were resolved by the operating system" is a statement about what was not checked. It must never be represented, quoted or summarized as evidence that the root was confined, isolated or custody-bounded.

### 1.3 Requirements proposed for the restricted qualification profile

Proposed, for Qualification to accept, amend or reject. Each is stated so that it can be tested.

| # | Requirement | Why |
|---|---|---|
| R8-1 | The profile names the authorized custody boundary for the environment: an absolute, normalized directory that is the highest directory the profile permits a handoff root to live under. | Without a stated boundary there is nothing to be escaped. |
| R8-2 | The profile carries a root and ancestor-chain policy for that environment: either (a) every component from the boundary down to the root is verified not to be a symlink, or (b) a named, enumerated set of permitted symlinked ancestors, each with its expected resolved target, verified at read time. A policy that is "any ancestor may be a symlink" does not satisfy the requirement. | Q8 requires "a verified root and ancestor-chain policy appropriate to that environment". Option (b) preserves the legitimate-symlink case without making it silent. |
| R8-3 | The resolved real path of the root must lie inside the authorized custody boundary. A root whose resolved path is outside it is refused. | Q8: "Refuse paths escaping the authorized custody boundary". |
| R8-4 | Paths given as relative components, `..` segments, absolute paths inside a relative position, and embedded separators are refused where they would leave the boundary after resolution. | Traversal. |
| R8-5 | The check and the read are bound: the chain is verified against the same directory handle that is then read (descriptor-relative opens from a verified starting handle), not verified by path and then re-opened by path. | A path check followed by a path open leaves a swap window. |
| R8-6 | A profile record must say which of R8-1 to R8-5 were enforced. The record never reuses `root_ancestors_resolved_by_os: true` as a claim of enforcement; if the profile enforces the chain, the record carries a distinct, typed member for that fact (member name to be decided by the owner, not fixed here). | Keeps disclosure and enforcement as different facts. |
| R8-7 | Where the platform cannot support the needed primitives (descriptor-relative opens, no-follow flags), the profile refuses rather than degrades to a path-based check. | The existing reader already refuses without `dir_fd` (README "Stated limits"); the profile keeps that fail-closed direction. |

### 1.4 Negative and positive tests proposed (for Qualification to freeze; none frozen here)

| # | Case | Expected |
|---|---|---|
| T8-1 | Root's final component is a symlink | refused (as today) |
| T8-2 | An ancestor between boundary and root is a symlink not on the permitted set | refused under R8-2 |
| T8-3 | An ancestor on the permitted set resolves to its expected target | accepted, with the permitted-ancestor fact recorded |
| T8-4 | An ancestor on the permitted set whose target was changed | refused under R8-2 |
| T8-5 | Symlink swap: an ancestor directory replaced by a symlink between the policy check and the read, repeated with timing variation | refused or read from the originally verified handle, never read from the swapped location |
| T8-6 | Symlink swap: an ancestor symlink retargeted outside the boundary after verification | refused under R8-3 or R8-5 |
| T8-7 | Traversal: `..` components, absolute path in a relative field, mixed separators, encoded separators | refused where resolution leaves the boundary |
| T8-8 | A path that resolves inside the boundary through a permitted symlink and traversal together | judged by the resolved real path; accepted only if inside |
| T8-9 | Platform without the required primitives | refused, not degraded |
| T8-10 | The general (non-restricted) handoff record on a root with a symlinked ancestor | accepted as today, with `root_ancestors_resolved_by_os: true` unchanged (guards against universal refusal) |
| T8-11 | A restricted-profile record whose `root_ancestors_resolved_by_os` is read as proof of isolation by a consumer | consumer-side check: never treated as isolation |

Limits that remain (stated, not hidden): same-content replacement (a different inode with identical bytes) and A-B-A changes are not detected by the current reader (README "Stated limits", first bullet); hardlinks to a regular file are accepted; case-insensitive file systems keep the caller's spelling. These are existing limits of the general reader and this proposal does not claim to remove them.

### 1.5 Open questions (Q8)

1. Who defines the "authorized custody boundary" for each qualification environment, and where is it recorded (profile, environment lock or both)?
2. Is the permitted-symlinked-ancestor set (R8-2 option b) needed at all for the first restricted profile, or does the first profile take option (a) only?
3. Member name and placement of the typed enforcement fact (R8-6): is it a new member in `cognous-source-preserving-handoff/0` (not yet frozen, per Q4) or a separate profile record?
4. Does the restricted profile run on platforms beyond POSIX with `dir_fd` and `O_NOFOLLOW`?

## 2. Q10: tamper-evidence anchor external to the store

### 2.1 Current behavior (reading)

The workflow event store chains events by digest. Per its README: truncation of the tail is detectable only against a head the caller retained from `append` or `load`; a log can be rewritten wholesale by someone who can write the directory and recompute every digest; the chain gives tamper evidence, not tamper prevention or authenticity (`orchestration/workflow_store/README.md` line 87). A log shorter than a caller-held head is refused as `truncated`; a different digest at that sequence is `chain_broken` (line 58; `store.py:451` raises `truncated`, `store.py:455` raises `chain_broken`). When no head was retained, nothing detects the removal of trailing events.

**Wording follow-up for the Orchestrator owner (non-conforming text).** The README sentence "The chain gives tamper evidence, not tamper prevention or authenticity" (line 87) does not conform to the Q10 narrower-property wording, because it says "tamper evidence" without the qualifier. It needs a qualifier such as "local chain consistency with limited truncation detection" until an external anchor exists. This record does not edit the Orchestrator; the Orchestrator design-doc worker is separately proposing README edits, and this is input to that owner.

Chain scope: the store's chain is per workflow. Each event carries `workflow_id`; `sequence` runs 1..N within one workflow; the first event has predecessor null; `expected_head` is a `(sequence, digest)` pair that refuses a sequence below 1 (`store.py:309-314` `_build_event`, `:440-455` `_check_head`). The store is bounded at 1,000 workflows by default (`max_workflows`, a configurable upper bound per Q9).

### 2.2 Decision (Q10, EXTERNAL TO THE STORE)

1. The Orchestrator must not be the sole custodian of the anchor used to verify its own event history.
2. An independently retained digest and count checkpoint is required, owned by the designated evidence or attestation custodian.
3. Qualification independently verifies the checkpoint during acceptance, but does not become the operational evidence store. Verification at acceptance is a point-in-time check against a checkpoint someone else holds. What Qualification holds at acceptance is left open (section 2.6 item 4).
4. Until an external anchor exists, the accurate statement is the narrower property: local chain consistency with limited truncation detection. The records, documentation and any claim text must not say "tamper-evident" without that qualifier, and must not claim complete tamper-evidence or authenticity.

### 2.3 Wording to use until an external anchor exists

Permitted: "The event log is a digest chain. It is locally consistent when every event's digest and predecessor link verify. Truncation is detected only against a head retained by the caller; a wholesale rewrite by a party able to write the store directory is not detected."

Not permitted: "tamper-evident store", "tamper-proof", "authentic event history", "independently verified history", or any statement that implies the history was attested, unless an external checkpoint exists and was verified for that history.

### 2.4 Proposed checkpoint record (closed shape, not frozen)

A proposal for the owner and Qualification to amend. The profile name is a placeholder and is not registered; nothing here is a wire-name freeze (see Q4 in [2.3-decision-corrections.md](2.3-decision-corrections.md): each profile freezes independently at its own qualification boundary).

Proposed placeholder profile: `ocs-event-checkpoint/0` (candidate name, unregistered).

A checkpoint is a JSON object with exactly these members; an unknown or missing member is refused. It follows the canonical form and digest of step 2.1 (RFC 8785 subset via `tools/registry_records.py`) if the owner adopts it.

| Member | Content |
|---|---|
| `profile` | the profile name above |
| `schema_version` | `0` |
| `canonical_profile` | `rfc8785-jcs` |
| `store_ref` | text naming the store (an identifier, not a path) |
| `workflow_id` | text: the workflow whose chain is described. The chain is per workflow, so a checkpoint is per workflow; a store with many workflows needs one checkpoint per workflow or a store-level aggregate (open question 2.6 item 8) |
| `sequence` | integer at least 1: the number of events in that workflow's chain at the checkpoint (equal to the sequence number of the last event; this matches the store's `expected_head`, which refuses a sequence below 1) |
| `head_digest` | `sha256:` plus 64 lowercase hex; the digest of the event at `sequence`. There is no checkpoint for an empty chain (no event, no head); how an empty or not-yet-started workflow is covered is an open question (2.6 item 9) |
| `custodian_ref` | text naming the designated evidence or attestation custodian that retains this checkpoint (a reference, not an identity proof) |
| `retained_at` | RFC 3339 UTC text: when the custodian retained it (a custodian assertion, not a verified clock) |
| `digest` | `sha256:` plus 64 lowercase hex over the other members |

Closed-shape rules proposed:

1. No verdict members. The record carries no `verdict`, `status`, `valid`, `passed`, `accepted`, `authentic` or similar member, and no authorization or pin selection. It states a count and a head; judgment about whether a store matches belongs to the verifier of the checkpoint.
2. Checkpoints for one (`store_ref`, `workflow_id`) are monotone in `sequence`; a later checkpoint with a smaller `sequence` is itself evidence of rollback and is reported, not hidden.
3. Verification (at acceptance, by Qualification) is a comparison: the store, loaded read-only, must contain at least `sequence` events and the event at `sequence` must have digest `head_digest`. A shorter store is `truncated`; a different digest is `chain_broken` (existing code names in the store). A store longer than the checkpoint is not an error: events appended after the checkpoint are not covered by it.
4. The checkpoint is held by the custodian, not inside the store directory and not written by the store's own process. A checkpoint stored next to the log it checks does not satisfy Q10.
5. A checkpoint does not make history authentic. It limits undetected truncation and rewrite to events after the latest checkpoint the verifier holds; it says nothing about whether the events were true. Authenticity needs signed provenance, which is not proposed here.

### 2.5 What this improves and what stays limited

| Threat | Local chain only | With an external checkpoint |
|---|---|---|
| Tail truncation, caller kept no head | not detected | detected up to the latest checkpoint |
| Wholesale rewrite with recomputed digests | not detected | detected for the range at or before the latest checkpoint (the head digest at `sequence` differs) |
| Truncation or rewrite after the latest checkpoint | not detected | not detected until the next checkpoint |
| False events appended | not detected | not detected |
| Custodian collusion or compromise | n/a | not covered |
| Authenticity of event content | not claimed | not claimed |

Checkpoint frequency (how stale the latest checkpoint may be) is therefore a property to state, not to hide.

### 2.6 Open questions (Q10): who is the custodian

1. Who is the designated evidence or attestation custodian: the evidence-attestation component in [component-lock.json](../../../component-lock.json) (`bitrep`, `cogno-us/cognous-evidence-attestation`), the evidence registry component (`the_index`, `cogno-us/cognous-evidence-registry`), a human operator, or another party? The Q10 text says only "the designated evidence or attestation custodian" and does not name one. This record does not decide it.
2. Does the chosen custodian already have a custody mechanism that fits a count and head pair, or is a new effect surface needed (a change that needs its own authorization)?
3. Who creates a checkpoint, and when: at each acceptance, at a set cadence, or at each terminal workflow event? How is a checkpoint transferred to the custodian without the Orchestrator being its sole holder?
4. What does Qualification hold at acceptance: a read-only copy of the latest checkpoint, or a query to the custodian at that moment? (Q10: Qualification verifies at acceptance, is not the operational store.)
5. Is a signature or other authentication of the checkpoint wanted later, and by whom? (This proposal does not include it.)
6. How are a lost checkpoint, a custodian change and a store reset (a new `store_ref`) handled?
7. Does the same mechanism also serve the Q9 cached chain head (a cached head must be verified and its persistence and restart behavior tested; an external checkpoint is a separate, independent check on it)?
8. Per-workflow scope: with a per-workflow chain and a 1,000-workflow default bound, is the checkpoint one record per workflow, or a store-level aggregate (for example a digest over the per-workflow heads with a workflow count)? Who bears the volume if checkpoints are frequent?
9. Empty chain: a workflow with no events has no head. Is its absence anchored (a checkpoint of workflow count, so a removed workflow is detected), or accepted as a limit?
