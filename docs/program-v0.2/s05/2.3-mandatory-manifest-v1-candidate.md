## What `applicability` means

Each check carries `{"kind": "unconditional"}` or `{"kind": "required_when_applicable", "predicate": <id>}`. The predicate
set is closed and declared in the manifest (`predicates`); a predicate is a name, a `basis` from the closed set
(`input_presence`, `input_state`, `peer_results`, `record_class`, `record_content`), source citations and a closed list
of justification codes. There is no free text, regex or expression. A predicate here names the condition under which
the verifier at the pinned revision EMITS the check at all (a check that the verifier would never produce for that input
cannot be executed). It does not name conditions under which the verifier emits a could-not-check abstention: those
checks are emitted and stay applicable (open question 1).

Because the module cannot read the inputs, an inapplicable disposition is a claim by the caller, as a `not_applicable`
outcome is under `/0`. The manifest and module bind the claim to the exact predicate, a justification code from that
predicate's closed list and the exact evaluator pair; they do not prove that the predicate is false. Proof belongs to
Qualification's independent cases.

## Early-return paths and the closed justification sets

`_evaluate` returns early in two cases, before any identity, ledger, journal-rule, lifecycle, profile or input-kind check is produced: the run record did not parse (`engine.py:200-210`, only `v1.wire.strict-parse` and `v1.structure.run-record` result; code `run_record_not_parsed`) and `verify_document` raised (`engine.py:212-216`, same two ids, the second as an error). `evaluate` still runs the V3 tier and the coverage fallback afterwards (`engine.py:153-168`), so the V3 predicates and `v2.coverage.items-examined` are unaffected.

- Not-parsed path: every predicate whose check is produced after the early return carries the justification `run_record_not_parsed`: the twelve predicates for the record-class, structure, input-presence and profile checks (`record_class_*`, `journal_record_*`, `*_profile_active_in_journal_record`, `non_journal_record_with_unread_inputs`). `v1.structure` has it already, `holder_inventory_reference_emitted` has `record_not_parsed_to_object`, the V3 witness and inventory-document predicates are emitted on this path.
- Exception, left to the architect: the `verify_document` crash path (`engine.py:212-216`). The same checks are absent, but no justification code is provided: a checker crash is an error, not an inapplicability, and recording it as inapplicable would hide the crash. This belongs to open question 7 (group crashes) and is listed there as one case. Until decided, a run on that path cannot complete these checks by disposition and must report an `error` outcome for the ids it cannot produce, or refuse.

## Per-check not-applicable reasons

Unchanged from `/0`: the `no_items_in_record` and `no_journal_in_record` reasons stay per check. They describe an executed
check that found nothing to examine (`engine.py:76-87`, `270`; `witness.py:673-680`; `documents.py:85-86`), which is a
different fact from inapplicability by predicate: the first is an executed result with a reason, the second is a
disposition with a predicate.

## Open questions for the architect (not guessed here)

1. Emitted-but-abstaining checks. For a journal the verifier emits the seven `v4.ledger.*` ids as could-not-check
   `input_absent:destination_ledger` when no ledger is supplied (`engine.py:317-319`), the seven `v2.identity.*` ids as
   `input_absent:proposal_export` when no proposal export is supplied (`identity.py:184-185`), and
   `v3.holder-inventory.record-reference` with `input_absent:holder_inventory`. Those are real abstentions, not omissions.
   The source does not say whether a missing optional input should make these checks inapplicable (a policy decision that
   would convert an abstention into an inapplicable disposition) and the four executed outcomes of the manifest have no
   outcome that maps the `input_absent:*` and `tier_unavailable:*` could-not-check reasons. They are therefore marked only by
   record class, not by input presence. Decide the mapping of could-not-check reasons to the four outcomes, and whether any
   `input_absent:*` reason is a justification.
2. Failure-path surrogates. `v1.structure.run-record` is emitted only when the run record did not parse or the checker
   crashed (`engine.py:200-216`), and `v1.structure` only when it did; a normal run emits `v1.structure` and never
   `v1.structure.run-record`. `v2.coverage.items-examined` is emitted only when nothing beyond V1 was confirmed
   (`engine.py:158-168`). Under `/0` they were unconditional, so no normal run could be complete. They are retained
   (Q3: no pruning) with mutually exclusive predicates. Confirm that they belong in the mandatory catalogue at all, and
   whether the module should check the exclusivity of `v1.structure` and `v1.structure.run-record` from the executed list.
3. `input_read.*` ids are derived from `MANDATORY_KINDS`, not emitted verifier results; confirm what executing one means
   and whether it is conditional on record class (the completion rule applies to journal records and `resolution_checks`).
4. Structure-refuted runs. Several predicates include "V1 structure confirmed": when the structure is refuted the verifier
   emits a skip list and other ids are not produced (`engine.py:246-257`, `documents.py:317-330`). Confirm that a refuted
   structure is a legitimate justification (`v1_structure_not_confirmed`) rather than a reason to refuse completeness.
5. `v3.holder-inventory.document` can also emit a could-not-check reason `not_applicable_to_input:inventory_enumerates_no_holder`
   (`witness.py:580`), a reason outside the closed not-applicable set; it is not modelled (as in `/0`).
6. Floor membership. The floor remains code and unconditional (`floor_check_conditional` refuses a conditional floor
   check). No floor id is chosen here.
7. Crash non-emission. When `verify_document` raises (`engine.py:212-216`) or a whole group raises, the verifier emits one fallback id instead (`v2.decisions`, `v2.identity`, `v4.ledger`, `v3.tier`; `engine.py:281`, `314`, `334`, `187`) and the group's catalogue ids are not emitted. Those four ids are excluded from the catalogue and no justification code covers a group crash, so a crash cannot be recorded as inapplicable. Decide whether a crash is an `error` outcome of each id or needs a justification.
8. Predicate truth is self-asserted (above). Who evaluates a predicate, and from which inputs, is for the evaluator
   qualification package (2.4 and Qualification), not for this data.
