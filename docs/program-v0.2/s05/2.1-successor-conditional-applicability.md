# Step 2.1 successor amendment (proposal, docs only): conditional applicability in `ocs-registry-record/1`

**Proposal, non-authorizing, documentation only.** Release and production remain on HOLD. Nothing here changes
`tools/registry_records.py`, the 2.1 tests or any record of profile `ocs-registry-record/0`, which stay as merged.
No registry activation code is proposed or authorized (step 2.4 is not authorized). Qualification owns the independent cases and verdicts; none is written
here. This note answers architect decision Q3: "this requires a versioned amendment to the current 2.1/2.3 semantics
because 2.1 currently rejects conditional mandatory rules. Do not simply weaken that invariant or make every conditional
check optional."

Companion records: [2.1-registry-records.md](../s04/2.1-registry-records.md) (current behavior),
[2.3-mandatory-check-contract.md](2.3-mandatory-check-contract.md) section 13 (manifest profile `/1` and completeness),
[2.3-mandatory-manifest-v1-candidate.md](2.3-mandatory-manifest-v1-candidate.md) (predicates).

## 1. What 2.1 does today and why it must not be weakened

- A rule entry's `applicability` is `{"kind": "always"}` or `{"kind": "predicate", "predicate": <text>, "source_ref": <text in source_refs>}`
  (`registry_records.py`, `_validate_rule`). The `predicate` is free text.
- `validate_record(record, floor_mandatory_rule_ids=...)` refuses a floor rule that is missing (`mandatory_check_missing`), not `required`
  (`mandatory_check_not_required`) or not `always` (`mandatory_check_conditional`). The 2.1 note gives the reason: no source predicate is proven by that code.
- The 2.3 module additionally refuses any manifest check whose rule entry is not `required` and `always` (`registry_rule_not_required`).

The invariant protects the floor from a registry entry that makes a constitutional check conditional with an unproven free-text predicate. That
protection stays. What is missing is a way for a NON-floor mandatory check to say "required, when this named, source-backed, closed condition holds",
so that the 51-id verifier catalogue can be kept whole (Q3) without making every check unconditional or optional.

## 2. What a successor profile `ocs-registry-record/1` would need

Version identity: profile `ocs-registry-record/1`, `schema_version` 1. A `/0` record keeps its profile, digest and behavior. All changes below
apply to `/1` only. Candidate names for the wire-name freeze; none is frozen.

### 2.1 Rule-entry `applicability` member

Same member name, three kinds:

| kind | members (exactly) | allowed for |
|---|---|---|
| `always` | `kind` | any status |
| `predicate` | `kind`, `predicate`, `source_ref` | `advisory` rules only (unchanged free-text semantics; never mandatory) |
| `required_when_applicable` | `kind`, `predicate`, `source_ref` | `required` rules only |

For `required_when_applicable`: `predicate` is a closed identifier (proposed grammar: lowercase ASCII letters, digits and underscore, 1 to 128 characters; never
free text, a regex or an expression); `source_ref` must be a member of the record's `source_refs` (as for the current `predicate` kind). The identifier names a
predicate declared in a `ocs-mandatory-manifest/1` manifest; 2.1 does not know that set.

### 2.2 Invariants to add or keep in `validate_record`

1. Kept and unchanged: a floor rule must be `required` and `always`; `mandatory_check_conditional` still refuses `required_when_applicable` for a floor id.
   The floor stays unconditional and in code.
2. New: a `required` rule may not use applicability kind `predicate` (free text); a `required` rule is `always` or `required_when_applicable`. An `advisory` rule may not use
   `required_when_applicable`. Refusal code: `schema_invalid` (no new code needed), or a precise new code if the owner prefers.
3. New: the identifier grammar above, checked by shape (no free text), and `source_ref` membership.
4. Kept: unique `(rule_id, class, profile)` scope; reason map and source-ref integrity; evaluator listing and qualification.
5. Digest, canonical profile and floor passing are unchanged: the digest still covers the whole record, so changing a rule's applicability changes the record digest.

### 2.3 What 2.1 cannot check (stays in 2.3)

2.1 has no manifest. These cross-document facts are checked by the 2.3 completeness function and would not move into 2.1:

- the rule entry's predicate id equals the predicate of the manifest check with the same id (refusal `predicate_mismatch`);
- the manifest declares that predicate (`unknown_predicate`) and the check is `required_when_applicable` there;
- a manifest check that is `unconditional` has `required`, `always` entries (`registry_rule_not_required`);
- every rule entry's evaluator pair equals the manifest check's (`rule_evaluator_mismatch`).

2.3 section 13 states these rules and its tests exercise them through an internal seam that models a `/1` rule entry; no registry code is involved.

### 2.4 Store, succession and migration (A2) consequences

- `RegistryStore._read` and `publish` validate with the single `PROFILE` constant. A store that holds both profiles needs explicit profile dispatch and a rule
  for which profiles may follow which: `check_succession` compares `epoch` and `predecessor` digest only, so a `/1` record could follow a `/0` record without a
  change. Whether it may is a migration decision for A2; this note does not decide it. A `/0` record must not be reinterpreted as `/1`.
- Until a `/1` record validator exists, `check_completeness` refuses every `required_when_applicable` manifest check against a `/0` record with
  `applicability_unsupported_by_registry`, because `/0` cannot express it. Unconditional checks continue to work against `/0`.

## 3. What this amendment does not do

- It does not authorize a `/1` registry implementation, activation, a pin selection or any change to a locked component.
- It does not decide which checks are conditional: that is the manifest data (a candidate in `2.3-mandatory-manifest-v1-candidate.json`).
- It does not claim a predicate is true: a predicate is a named, cited condition; whether it holds for a given input is an evaluator question for Qualification.
- It does not touch the 1.3 contract or the register.

## 4. Impact and next gate

Affects `tools/registry_records.py` and `tests/test_registry_records.py` (new profile, shape rules, store dispatch) and the F3 impact assessment for any consumer of
registry records. Gate (Q13): the revised mandatory-check contract and evaluator binding are frozen, applicability and negative controls are independently approved,
the affected component and pin impact is reconciled, and the operator authorizes the exact 2.4 package. None of that is claimed here.

## 5. Questions for the architect

1. Is the `/1` kind name `required_when_applicable` and the `required` versus `predicate` split acceptable, or should `predicate` be withdrawn entirely in `/1`?
2. May a `/1` record succeed a `/0` record directly (epoch and predecessor), or is a migration record required (A2)?
3. Should the predicate identifier grammar be fixed in 2.1, or is membership in a manifest-declared set (checked in 2.3) enough?
