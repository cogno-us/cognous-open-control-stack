# Step 2.3: mandatory check manifest and evaluators contract (candidate, docs only)

**Candidate contract, non-authorizing.** Release and production remain on HOLD. This record defines a versioned data profile that lists the mandatory checks and a completeness function over executed results. It activates nothing (activation is step 2.4), selects no pin, grants nothing, changes no locked component and no floor, and has no effect surface. Qualification owns the independent cases and every verdict; nothing here is posted to its controller. Profile and member names are candidates for the wire-name freeze. Nothing here claims that any component is qualified, certified or ready for any use.

Scope: step 2.3 in [engineering-register.json](../engineering-register.json) (title "Mandatory check manifest/evaluators", dependency 2.1; acceptance and exit criteria: "no skipped mandatory check"; estimate basis: "the floor stays code, registry references evaluators"). Contract inputs: [1.3 registry R0](../s02/contracts/1.3-registry-r0.md) sections 2.2 to 5, [2.1 registry records](../s04/2.1-registry-records.md), [2.2 scanner-rule profile](../s04/2.2-scanner-profile-contract.md).

Companion records (their contents are not asserted here): the manifest data `docs/program-v0.2/s05/2.3-mandatory-manifest.json`, the reference module `tools/mandatory_checks.py`, and its tests.

## 1. Purpose and boundary

Problem: a decision that runs fewer mandatory checks than the policy requires must be detectable, not silent. 1.3 section 2.2 records that check resolution is procedural in the Control Plane (no table) and that the nearest manifest is the verifier set; section 5 requires that the resolver "never falls back to a smaller manifest".

The manifest is the total list of mandatory checks as data. `check_completeness` compares that list with what was executed and either returns a report or refuses. It never judges the checks.

| Owner | Responsibility |
|---|---|
| Component that owns the gate | The floor (the mandatory check ids), in code, passed explicitly; running the checks; activation |
| Registry (2.1 record) | Rule entries that reference evaluators by id and version; evaluator `qualification_ref` |
| This profile | The closed list of checks, input kinds and not-applicable reasons, with source provenance |
| Qualification | Independent cases, expectations, oracles, evaluator qualification, verdicts |

## 2. Manifest profile `ocs-mandatory-manifest/0`

A manifest is a JSON object with exactly these members; unknown or missing members are refused.

| Member | Content |
|---|---|
| `profile` | `ocs-mandatory-manifest/0` |
| `schema_version` | `0` |
| `canonical_profile` | `rfc8785-jcs` |
| `manifest_id` | non-empty text |
| `digest` | `sha256:` plus 64 lowercase hex |
| `sources` | list of source entries |
| `input_kinds` | sorted unique non-empty texts: the mandatory input kinds |
| `not_applicable_reasons` | sorted unique non-empty texts: the closed reason set |
| `checks` | list sorted by `check_id` |

`sources[]` members, exactly: `source_id` (unique), `repository`, `revision` (40 lowercase hex), `path`, `lines` (text such as `951-955`, may be empty), `note`.

`checks[]` members, exactly: `check_id` (unique, non-empty), `kind` (`verifier_check` or `input_read`), `source_id` (must name a source), `input_kind` (a member of `input_kinds` or null; non-null is required when `kind` is `input_read`), `evaluator_id`, `evaluator_version` (integer, at least 1), `not_applicable_reasons` (sorted, a subset of the manifest's closed set, possibly empty).

Every listed check is mandatory. There is no optional flag and no status member: an advisory check does not belong in this manifest.

Determinism: canonical form and digest are exactly those of step 2.1 (`tools/registry_records.py`: `jcs_dumps`, `loads_strict`, `record_digest`), that is, RFC 8785 for the subset in 2.1 (no floats, no duplicate keys, no lone surrogates) and `sha256:` over the object without its `digest` member. The reference module reuses these functions and does not reimplement canonicalization ([2.1 note](../s04/2.1-registry-records.md), "Canonical JSON" and "Record digest" rows). Set-valued arrays are sorted by code point and `checks` by `check_id`; an unsorted array is refused as `schema_invalid`. The digest of the manifest is held outside it by the caller as a pin; the claim is "pinned and immutable", not "signed" (1.3 section 4).

## 3. Relationship to the 2.1 registry record and the 2.2 scanner profile

2.1 (`tools/registry_records.py`): a record has `rule_table` entries (members `rule_id`, `version`, `class`, `profile`, `status`, `applicability`, `evaluator_id`, `evaluator_version`, `failure_disposition`, `missing_treatment`, `reason_code`, `source_ref`) and `evaluators` entries (`evaluator_id`, `version`, `qualification_ref`). `validate_record` requires the caller to pass `floor_mandatory_rule_ids` explicitly (no default) and refuses a floor rule that is missing, not `required`, or conditional; it refuses an evaluator that is unknown or has an empty `qualification_ref`.

2.3 adds, with no 2.1 change:

- The manifest is a separate record. The 2.1 record references checks by rule entry: each manifest `check_id` must equal the `rule_id` of an entry that is `required` with applicability `always`. The manifest does not live inside the 2.1 record, and the record does not embed manifest content; a typed reference member would need a new 2.1 profile version (not proposed; compare the same consequence recorded for scanner rulesets in 2.2 section 4).
- The floor is a code-side set of check ids. `check_completeness` requires it as an explicit argument and requires it to be a subset of the manifest, so a manifest cannot drop a floor check. The manifest can add checks above the floor; it cannot remove or weaken one. The floor stays code.
- Evaluators are referenced, not defined: the manifest names `evaluator_id` and `evaluator_version`; the 2.1 record's `evaluators` list carries the `qualification_ref`.

2.2: scanner rules are one rule family in a 2.1 record (class `scanner`, source reference to an `ocs-scanner-ruleset/0` digest). The manifest covers mandatory checks, not scanner patterns, and carries no pattern text. A scanner rule becomes a manifest check only if the owner of the floor decides so and it is `required` and `always`; 2.2 leaves scanner rule status undecided and the illustrative 2.2 record uses `advisory` (2.2 section 4). The deferred 2.2 entry is never mandatory (2.2 section 5).

## 4. Completeness semantics (`check_completeness`)

Signature: `check_completeness(manifest, record, executed, *, floor_check_ids, pin=None) -> dict`. `executed` is a list of objects with exactly `check_id`, `outcome` (`passed`, `failed`, `not_applicable`, `error`), `reason` (text for `not_applicable`, otherwise null), `evaluator_id`, `evaluator_version`. Steps run in this order and the first failing step refuses, naming one code; nothing is changed.

1. Validate the manifest (`validate_manifest`; with `pin`, the digest must equal it). Codes: `schema_invalid`, `digest_mismatch`, `pin_mismatch`, `duplicate_check`, `unknown_source`, `unknown_input_kind`, `unknown_reason`.
2. Require `floor_check_ids` to be a subset of the manifest's checks: `floor_not_in_manifest`.
3. Validate the record with `registry_records.validate_record(record, floor_mandatory_rule_ids=floor_check_ids)`; any 2.1 refusal is wrapped as `registry_record_invalid`.
4. Require every manifest check to have a rule entry with the same id, status `required`, applicability `always`: `registry_rule_missing`, `registry_rule_not_required`.
5. Check each executed entry: names a manifest check (`unexpected_check`), appears once (`duplicate_result`), has a valid outcome (`invalid_outcome`; this contract proposes the same code for a wrong member set, to be confirmed against the module), matches the manifest's evaluator id and version (`evaluator_mismatch`), and that evaluator is in the record's `evaluators` with a non-empty `qualification_ref` (`unqualified_evaluator`; this contract proposes `unknown_evaluator` when the pair is absent from `evaluators` altogether, to be confirmed against the module). A `not_applicable` outcome needs a `reason` in that check's allowed list: `not_applicable_reason_not_allowed`.
6. Require every manifest check to have a result: `skipped_mandatory_check`, listing the missing ids.

Closed refusal code set (19): `schema_invalid`, `digest_mismatch`, `pin_mismatch`, `duplicate_check`, `unknown_source`, `unknown_input_kind`, `unknown_reason`, `unknown_evaluator`, `unqualified_evaluator`, `floor_not_in_manifest`, `skipped_mandatory_check`, `unexpected_check`, `duplicate_result`, `not_applicable_reason_not_allowed`, `evaluator_mismatch`, `invalid_outcome`, `registry_record_invalid`, `registry_rule_missing`, `registry_rule_not_required`.

Report, returned only on success, exactly: `manifest_digest`, `record_digest`, `complete` (always true; an incomplete case raises instead of returning), `counts` (per outcome) and `checks` (list of `check_id`, `outcome`, `reason` in manifest order).

Why there is no verdict. Completeness answers one question: did every mandatory check run, or close as a permitted not-applicable? Whether the decision is allowed is the gate's business. The report holds no pass/fail judgment, grant, pin selection or activation, so it cannot be mistaken for authorization. A `failed` or `error` outcome is reported as itself: hiding or dropping it would make the report look cleaner than the run, and treating `error` as "not run" would let a crashing check read as a skip. A caller that sees `failed` or `error` in a complete report applies its own failure disposition from the 2.1 rule entry. Completeness never converts `failed` or `error` into `passed` or `not_applicable`.

## 5. Not-applicable

A check may close as `not_applicable` only with a `reason` drawn from that check's `not_applicable_reasons`, itself a subset of the manifest's closed set. Never open text: free text, an empty string, a reason from another check's list or a reason in the manifest set but not in the check's list is refused (`not_applicable_reason_not_allowed`). A reason outside the manifest set is refused at manifest validation (`unknown_reason`). A check with an empty list can never close as not-applicable. A rule entry with a predicate applicability is refused for a mandatory check (`registry_rule_not_required`, or `registry_record_invalid` when the floor catches it first), because no source predicate is proven by this code (2.1 note, "Floor" row; 1.3 section 5, third bullet).

The vocabulary and its source are in the companion manifest. 1.3 section 2.2 records two reasons at the verifier, `no_items_in_record` and `no_journal_in_record`, as "already a closed set"; whether each may apply to a given check is a data decision made per check in the manifest, not by this contract.

## 6. Evaluator qualification

The manifest names evaluator id and version per check. Executed results must report the same id and version (`evaluator_mismatch` otherwise), and the 2.1 record must list that pair in `evaluators` with a non-empty `qualification_ref` (`unqualified_evaluator`; absent pair `unknown_evaluator`). Version equality is exact: a different version is a different evaluator and needs its own record entry. A `qualification_ref` is a reference string supplied by Qualification; this code checks only that it is non-empty and does not verify what it points to. Until Qualification supplies one, completeness refuses with `unqualified_evaluator`; that refusal is intended (compare 2.2 section 4, last paragraph).

## 7. What the manifest does not do

- It does not decide pass or fail, and has no verdict member.
- It does not grant, select or hold a pin, or authenticate; the pin is a digest held outside it.
- It does not activate a rule set or bind a digest into any decision (step 2.4 and the F3 packages).
- It does not change the floor. The floor is code owned by the gate component; the manifest can only be a superset, and a floor id missing from it is refused (`floor_not_in_manifest`).
- It does not run checks, read inputs or contain evaluator code or patterns.
- It does not make a check mandatory by being listed in some other document; only presence here plus a `required`, `always` rule entry does.
- It is not independently qualified. Developer tests, when present, show that they exercise the rules, not that the rules are sufficient (as stated for 2.1).

## 8. Open decision: refusal input types, 5 versus 11

1.3 section 2.2 records that the Control Plane lists 5 refusal input types (`grant`, `policy`, `approval`, `evidence`, `role_mapping`; `bounded.py` `RefusalInputVersion`) and the ODES execution-attempt-lifecycle schema lists 11 (adds `manifest`, `authority_context`, `identity`, `mandate`, `conflict`, `purpose`). The enumerations disagree. This contract does not resolve it. This profile's `input_kinds` are the mandatory input kinds (1.3 section 2.2 lists 7 at the verifier, `rules_journal.py:951`), a related but different set; the refusal input types are what a refusal may name as the input that was missing or stale.

| Option | Effect | Cost |
|---|---|---|
| A. Keep both; the manifest names its own kinds and states no mapping | No locked change; disagreement persists | A refusal naming a kind outside the Control Plane's 5 cannot be represented there |
| B. Align the Control Plane to the 11 | One enumeration | Locked change to the Control Plane and its ODES contract: F3 requalification and re-review |
| C. Narrow ODES to the 5 | One enumeration | Locked change to ODES and a possible loss of kinds the lifecycle needs (for example `identity`, `mandate`, `conflict`) |
| D. Record an explicit mapping table (manifest input kind to refusal input type, with "none" allowed) as data, owned by Qualification-frozen cases | No locked change now; makes the gap visible | A mapping is only as good as its review; it cannot add a type to the Control Plane |

Recommendation: D now, as a documented data mapping with the gap shown, and B as a separate F3 proposal if the operator wants one enumeration. Do not choose C without evidence that the lifecycle does not need the six extra kinds. This is a recommendation, not a decision.

| 6 | `checks[].kind` outside the two names | `schema_invalid` |
| 7 | `kind` `input_read` with `input_kind` null | `schema_invalid` |
| 8 | Declared digest differs from the canonical digest | `digest_mismatch` |

| 10 | Two checks with the same `check_id` | `duplicate_check` |

| 13 | Check reason outside the manifest's closed set | `unknown_reason` |
| 14 | `floor_check_ids` contains an id the manifest lacks | `floor_not_in_manifest` |
| 15 | Record invalid under 2.1 (for example unqualified floor evaluator, digest mismatch) | `registry_record_invalid` |
| 16 | Manifest check with no rule entry in the record | `registry_rule_missing` |
| 17 | Rule entry `advisory` for a manifest check | `registry_rule_not_required` |
| 18 | Rule entry with predicate applicability for a manifest check | `registry_rule_not_required` (or `registry_record_invalid` if it is also in the floor) |
| 19 | Executed list omits one mandatory check | `skipped_mandatory_check` |
| 20 | Executed list is empty | `skipped_mandatory_check` |
| 21 | Executed entry names a check not in the manifest | `unexpected_check` |
| 22 | Same `check_id` executed twice, even with equal outcomes | `duplicate_result` |
| 23 | `outcome` outside the four names, or extra or missing member in an executed entry | `invalid_outcome` |
| 24 | `not_applicable` with a reason not in that check's list | `not_applicable_reason_not_allowed` |
| 25 | `not_applicable` with null or empty reason, or free text | `not_applicable_reason_not_allowed` |
| 26 | Executed `evaluator_id` or `evaluator_version` differs from the manifest | `evaluator_mismatch` |
| 27 | Evaluator not listed in the record `evaluators` | `unknown_evaluator` |
| 28 | Evaluator listed with empty `qualification_ref` | `unqualified_evaluator` |
| 29 | A `failed` or `error` outcome with every check present | not a refusal: reported as itself with `complete` true (positive case that guards against hiding) |
| 30 | A passing call with a changed record or manifest afterwards | not a refusal: the inputs are unchanged by the call (no side effect) |

Cases 29 and 30 are positive guards; the rest are refusals.

## 10. Out of scope: activation and freshness (step 2.4)

Publication is not activation. Epoch ordering, predecessor linkage, the Control Plane gate, the pin held outside the store, an age bound for offline restart, UNKNOWN versus ACTIVE and binding the manifest digest into a decision context are step 2.4 and the F3 packages (1.3 sections 5 and 6; 2.1 note, "What it does not do"). This contract defines no freshness rule for a manifest and does not say how a manifest is selected for a given policy version, class, profile and assurance level (1.3 section 5 names that resolver; it is not built here).

## 11. Limits and assumptions

- Source provenance for each check is carried in the companion data; this contract states no check count. 1.3 section 2.2 states that the 44 verifier check identifiers and the Control Plane check bodies are not itemized in R0 and that itemizing them is a mechanical, source-backed step with an independent check by Qualification; the 2.3 estimate basis cites 44 verifier check ids and 369 procedural lines (`bounded.py:2239-2607`), at confidence LOW.
- Completeness is relative to the manifest: a check absent from the manifest and from the floor is not detected. The manifest is only as complete as its source itemization, which Qualification must check independently.
- The Control Plane resolution is procedural; no claim is made that it matches the manifest until that comparison is done and qualified.
- Wire names are candidates; a change before Qualification starts is cheap, afterwards it needs a new profile identifier.
- Standard library only; synthetic data; no network, subprocess or credential effects.
