## 1. Purpose and boundary

Problem: a decision that runs fewer mandatory checks than the policy requires must be detectable, not silent. 1.3 section 2.2 records that check resolution is procedural in the Control Plane (no table) and that the nearest manifest is the verifier set; section 5 requires that the resolver "never falls back to a smaller manifest".

The manifest is the total list of mandatory checks as data. `check_completeness` compares that list with what was executed and either returns a report or refuses. It never judges the checks.

| Owner | Responsibility |
|---|---|
| Component that owns the gate | The floor (the mandatory check ids), in code, passed explicitly; running the checks; activation |
| Registry (2.1 record) | Rule entries that reference evaluators by id and version; evaluator `qualification_ref` |
| This profile | The closed list of checks, input kinds and not-applicable reasons, with source provenance |
| Qualification | Independent cases, expectations, oracles, evaluator qualification, verdicts |

## 2. Manifest profile `ocs-mandatory-manifest/0`

A manifest is a JSON object with exactly these members; unknown or missing members are refused.

| Member | Content |
|---|---|
| `profile` | `ocs-mandatory-manifest/0` |
| `schema_version` | `0` |
| `canonical_profile` | `rfc8785-jcs` |
| `manifest_id` | non-empty text |
| `digest` | `sha256:` plus 64 lowercase hex |
| `sources` | list of source entries |
| `input_kinds` | sorted unique non-empty texts: the mandatory input kinds |
| `not_applicable_reasons` | sorted unique non-empty texts: the closed reason set |
| `checks` | list sorted by `check_id` |

`sources[]` members, exactly: `source_id` (unique), `repository`, `revision` (40 lowercase hex), `path`, `lines` (text such as `951-955`, may be empty), `note`.

`input_read` checks carry `check_id` exactly `input_read.<input_kind>` (refused as `schema_invalid` otherwise).

`checks[]` members, exactly: `check_id` (unique, non-empty), `kind` (`verifier_check` or `input_read`), `source_id` (must name a source), `input_kind` (a member of `input_kinds` or null; non-null is required when `kind` is `input_read`), `evaluator_id`, `evaluator_version` (integer, at least 1), `not_applicable_reasons` (sorted, a subset of the manifest's closed set, possibly empty).

Every listed check is mandatory. There is no optional flag and no status member: an advisory check does not belong in this manifest.

Determinism: canonical form and digest are exactly those of step 2.1 (`tools/registry_records.py`: `jcs_dumps`, `loads_strict`, `record_digest`), that is, RFC 8785 for the subset in 2.1 (no floats, no duplicate keys, no lone surrogates) and `sha256:` over the object without its `digest` member. The reference module reuses these functions and does not reimplement canonicalization ([2.1 note](../s04/2.1-registry-records.md), "Canonical JSON" and "Record digest" rows). Set-valued arrays are sorted by UTF-16 code unit (the RFC 8785 key order, as in the module and 2.1) and `checks` by `check_id`; an unsorted array is refused as `schema_invalid`. The digest of the manifest is held outside it by the caller as a pin; the claim is "pinned and immutable", not "signed" (1.3 section 4).

## 3. Relationship to the 2.1 registry record and the 2.2 scanner profile

2.1 (`tools/registry_records.py`): a record has `rule_table` entries (members `rule_id`, `version`, `class`, `profile`, `status`, `applicability`, `evaluator_id`, `evaluator_version`, `failure_disposition`, `missing_treatment`, `reason_code`, `source_ref`) and `evaluators` entries (`evaluator_id`, `version`, `qualification_ref`). `validate_record` requires the caller to pass `floor_mandatory_rule_ids` explicitly (no default) and refuses a floor rule that is missing, not `required`, or conditional; it refuses an evaluator that is unknown or has an empty `qualification_ref` only when a rule entry USES it (`registry_records.py:230-236`); an evaluator listed but used by no rule is not checked there (see section 6).

2.3 adds, with no 2.1 change:

- The manifest is a separate record. The 2.1 record references checks by rule entry: each manifest `check_id` must equal the `rule_id` of an entry that is `required` with applicability `always`. The manifest does not live inside the 2.1 record, and the record does not embed manifest content; a typed reference member would need a new 2.1 profile version (not proposed; compare the same consequence recorded for scanner rulesets in 2.2 section 4).
- The floor is a code-side set of check ids. `check_completeness` requires it as an explicit argument and requires it to be a subset of the manifest, so a manifest cannot drop a floor check. The manifest can add checks above the floor; it cannot remove or weaken one. The floor stays code.
- Evaluators are referenced, not defined: the manifest names `evaluator_id` and `evaluator_version`; the 2.1 record's `evaluators` list carries the `qualification_ref`.

2.2: scanner rules are one rule family in a 2.1 record (class `scanner`, source reference to an `ocs-scanner-ruleset/0` digest). The manifest covers mandatory checks, not scanner patterns, and carries no pattern text. A scanner rule becomes a manifest check only if the owner of the floor decides so and it is `required` and `always`; 2.2 leaves scanner rule status undecided and the illustrative 2.2 record uses `advisory` (2.2 section 4). The deferred 2.2 entry is never mandatory (2.2 section 5).

## 4. Completeness semantics (`check_completeness`)

Signature: `check_completeness(manifest, record, executed, *, floor_check_ids, pin=None) -> dict`. `executed` is a list of objects with exactly `check_id`, `outcome` (`passed`, `failed`, `not_applicable`, `error`), `reason` (text for `not_applicable`, otherwise null), `evaluator_id`, `evaluator_version`. Steps run in this order and the first failing step refuses, naming one code; nothing is changed.

1. Validate the manifest (`validate_manifest`; with `pin`, the digest must equal it). A supplied pin is compared with `is not None`: any pin that is not `None` and is not exactly the computed digest (an empty string, wrong case, truncated, any non-text type) is `pin_mismatch`, never `schema_invalid` and never treated as no pin. Codes: `schema_invalid`, `digest_mismatch`, `pin_mismatch`, `duplicate_check`, `unknown_source`, `unknown_input_kind`, `unknown_reason`.
2. Require `floor_check_ids` (explicit, no default; a set, frozenset, tuple or list of non-empty texts) to be a subset of the manifest's checks: `floor_not_in_manifest`. An empty `floor_check_ids` is refused as `schema_invalid` (an empty floor would protect nothing); a floor of the wrong type or with a non-text member is also `schema_invalid`.
3. Validate the record with `registry_records.validate_record(record, floor_mandatory_rule_ids=floor_check_ids)`; any 2.1 refusal is wrapped as `registry_record_invalid`.
4. Require every manifest check to have a rule entry with the same id, status `required`, applicability `always`: `registry_rule_missing`, `registry_rule_not_required`. Repair (Q2, section 13.1): every rule entry for the id must also use exactly the manifest check's evaluator id and version (`rule_evaluator_mismatch`), and that pair must be listed and qualified in the record (`unknown_evaluator`, `unqualified_evaluator`), all before any executed entry is read.
5. Check each executed entry: names a manifest check (`unexpected_check`), appears once (`duplicate_result`), has a valid outcome (`invalid_outcome`, only for an outcome text that is not one of the four names), matches the manifest's evaluator id and version (`evaluator_mismatch`); the listing and qualification of that pair moved to step 4 (section 13.1). Shape faults of the executed list are `schema_invalid` and are found before any of these per-entry checks: a list that is not a list, an entry that is not an object with exactly the five members, a non-text `check_id`, `evaluator_id` or `outcome`, a bad `evaluator_version`, or a `reason` that is neither text nor null. A text `reason` on an outcome other than `not_applicable` is also `schema_invalid`, found in that entry's turn after its other per-entry checks. A `not_applicable` outcome needs a `reason` in that check's allowed list: `not_applicable_reason_not_allowed`.
6. Require every manifest check to have a result: `skipped_mandatory_check`, listing the missing ids.

Closed refusal code set of profile `/0` as first written (19; the repaired module has 26, see section 13.5): `schema_invalid`, `digest_mismatch`, `pin_mismatch`, `duplicate_check`, `unknown_source`, `unknown_input_kind`, `unknown_reason`, `unknown_evaluator`, `unqualified_evaluator`, `floor_not_in_manifest`, `skipped_mandatory_check`, `unexpected_check`, `duplicate_result`, `not_applicable_reason_not_allowed`, `evaluator_mismatch`, `invalid_outcome`, `registry_record_invalid`, `registry_rule_missing`, `registry_rule_not_required`.

Report, returned only on success, exactly: `manifest_digest`, `record_digest`, `complete` (always true; an incomplete case raises instead of returning), `counts` (per outcome) and `checks` (list of `check_id`, `outcome`, `reason` in manifest order).

Why there is no verdict. Completeness answers one question: did every mandatory check run, or close as a permitted not-applicable? Whether the decision is allowed is the gate's business. The report holds no pass/fail judgment, grant, pin selection or activation, so it cannot be mistaken for authorization. A `failed` or `error` outcome is reported as itself: hiding or dropping it would make the report look cleaner than the run, and treating `error` as "not run" would let a crashing check read as a skip. A caller that sees `failed` or `error` in a complete report applies its own failure disposition from the 2.1 rule entry. Completeness never converts `failed` or `error` into `passed` or `not_applicable`.

## 5. Not-applicable

A check may close as `not_applicable` only with a `reason` drawn from that check's `not_applicable_reasons`, itself a subset of the manifest's closed set. Never open text: free text, an empty string, a reason from another check's list or a reason in the manifest set but not in the check's list is refused (`not_applicable_reason_not_allowed`). A reason outside the manifest set is refused at manifest validation (`unknown_reason`). A check with an empty list can never close as not-applicable. A rule entry with a predicate applicability is refused for a mandatory check (`registry_rule_not_required`, or `registry_record_invalid` when the floor catches it first), because no source predicate is proven by this code (2.1 note, "Floor" row; 1.3 section 5, third bullet).

The vocabulary and its source are in the companion manifest. 1.3 section 2.2 records two reasons at the verifier, `no_items_in_record` and `no_journal_in_record`, as "already a closed set"; whether each may apply to a given check is a data decision made per check in the manifest, not by this contract.

## 6. Evaluator qualification

The manifest names evaluator id and version per check. Executed results must report the same id and version (`evaluator_mismatch` otherwise), and the 2.1 record must list that pair in `evaluators` with a non-empty `qualification_ref` (`unqualified_evaluator`; absent pair `unknown_evaluator`). This paragraph and the limitation below are superseded by section 13.1: the binding is now mandatory. Version equality is exact: a different version is a different evaluator and needs its own record entry. A `qualification_ref` is a reference string supplied by Qualification; this code checks only that it is non-empty and does not verify what it points to. Until Qualification supplies one, completeness refuses; that refusal is intended (compare 2.2 section 4, last paragraph). The code depends on how the evaluator is used. `validate_record` already refuses a record whose rule entry uses an evaluator that is unlisted or has a blank `qualification_ref`, so for an evaluator used by a rule the refusal is `registry_record_invalid` and the step 5 evaluator check is not reached.

Limitation as first written (resolved by section 13.1; kept as a historical record): the module compares the manifest's evaluator with the executed entry and looks the manifest's evaluator up in the record, but it does not compare the manifest's evaluator with the evaluator of the rule entry that has the same id (module decision D9). Consequently `unknown_evaluator` is reachable for a manifest evaluator absent from `evaluators` (which no rule uses), and `unqualified_evaluator` is reachable only for an evaluator that is listed with a blank `qualification_ref` but used by no rule entry. Open question for the owner: should the manifest's evaluator be compared with the rule entry's evaluator (id and version), refusing a disagreement? Not decided here; no code change is made for it.

## 7. What the manifest does not do

- It does not prove not-applicable. A `not_applicable` outcome is self-asserted by the caller: the manifest permits a reason per check but does not prove the reason holds. The verifier's own guard (`engine.py:45-46`, `:262-272`, which rewrites `no_items_in_record` to `tier_unavailable:no_decisions_for_supplied_inputs` in some cases) is not modelled here.
- Relative completeness: `validate_manifest` alone accepts a zero-check manifest; `check_completeness` guards that only through `floor_not_in_manifest` (the floor must be a non-empty subset). A manifest shrunk to exactly the floor passes by design (section 11); the pin held outside the manifest is the only protection against a shrunk manifest.
- It does not decide pass or fail, and has no verdict member.
- It does not grant, select or hold a pin, or authenticate; the pin is a digest held outside it.
- It does not activate a rule set or bind a digest into any decision (step 2.4 and the F3 packages).
- It does not change the floor. The floor is code owned by the gate component; the manifest can only be a superset, and a floor id missing from it is refused (`floor_not_in_manifest`).
- It does not run checks, read inputs or contain evaluator code or patterns.
- It does not make a check mandatory by being listed in some other document; only presence here plus a `required`, `always` rule entry does.
- It is not independently qualified. Developer tests, when present, show that they exercise the rules, not that the rules are sufficient (as stated for 2.1).

## 11. Limits and assumptions

- Check-id count (Q7, current definition; 1.3 and the register are not edited here): the current catalogue is 51 itemized verifier check ids, so the manifest has 7 `input_read` plus 51 `verifier_check` = 58 checks. The 44 cited in the 1.3 contract and in the register's estimate basis is a historical count of literals, not the catalogue definition. Details: [2.3-mandatory-manifest.md](2.3-mandatory-manifest.md), "Counting the verifier check ids".
- Source provenance for each check is carried in the companion data. 1.3 section 2.2 states that the 44 verifier check identifiers and the Control Plane check bodies are not itemized in R0 and that itemizing them is a mechanical, source-backed step with an independent check by Qualification; the 2.3 estimate basis cites 44 verifier check ids and 369 procedural lines (`bounded.py:2239-2607`), at confidence LOW.
- Completeness is relative to the manifest: a check absent from the manifest and from the floor is not detected. The manifest is only as complete as its source itemization, which Qualification must check independently.
- The Control Plane resolution is procedural; no claim is made that it matches the manifest until that comparison is done and qualified.
- Wire names are candidates; a change before Qualification starts is cheap, afterwards it needs a new profile identifier.
- Standard library only; synthetic data; no network, subprocess or credential effects.

### 13.1 Evaluator identity (Q2, applies to both profiles)

The executed evaluator id and version must match BOTH the manifest check entry and every registry rule entry with that rule id. Steps, per manifest check in manifest order, before any executed entry is read:

1. `registry_rule_missing` (no entry); 2. for each entry in record order: `registry_rule_not_required` (status not `required`, or applicability not `always`), then `rule_evaluator_mismatch` when the entry's (`evaluator_id`, `evaluator_version`) differs from the manifest check's; 3. the manifest check's pair must be listed in the record `evaluators` (`unknown_evaluator`) with a non-blank `qualification_ref` (`unqualified_evaluator`). Then each executed entry must carry the manifest's pair (`evaluator_mismatch`).

A different but qualified evaluator is not interchangeable: a rule entry that names another evaluator or another version, even one listed and qualified, is `rule_evaluator_mismatch`; a new evaluator needs a versioned contract change (a new manifest and a new record). Qualification binds the exact pair: the `qualification_ref` that counts is the one on the entry with that id and version.

`rule_evaluator_mismatch` is a new precise code (not a reuse of `evaluator_mismatch`, which stays for executed versus manifest) so a registry/manifest disagreement is distinguishable from a run reporting the wrong evaluator. Scope note: these two codes are re-surfaced for ANY rule in the record, so they can concern a rule that no manifest check uses; the message names the first offending rule id and evaluator. `unknown_evaluator` and `unqualified_evaluator` are now reachable through the public function: `registry_records.validate_record` refuses first a record whose rule uses an unlisted or blank evaluator, and those two 2.1 inner codes are surfaced under their own names instead of `registry_record_invalid` (every other 2.1 refusal stays `registry_record_invalid`). The per-check pair look-up of step 3 is kept as an independent second guard; its direct tests use an internal registry view (`_complete`).

| Member | Content |
|---|---|
| `predicates` | list sorted by `predicate_id`; each exactly `predicate_id` (text), `basis` (one of `input_presence`, `input_state`, `peer_results`, `record_class`, `record_content`), `source_ids` (strictly increasing non-empty list of source ids), `justifications` (strictly increasing non-empty list of closed justification codes) |
| `checks[].applicability` | exactly `{"kind": "unconditional"}` or `{"kind": "required_when_applicable", "predicate": <predicate_id>}` |

A predicate is a named condition with source citations: its meaning is written in the companion record (candidate: [2.3-mandatory-manifest-v1-candidate.md](2.3-mandatory-manifest-v1-candidate.md)) and never evaluated by this module. No member holds free text, a regex or an expression. Validation adds: a declared predicate that no check uses is `schema_invalid`; a predicate `source_ids` entry naming no source is `unknown_source`; a check naming an undeclared predicate is `unknown_predicate`; other shape faults are `schema_invalid`.

Completeness for `/1` (`check_completeness(..., dispositions=None)`; a `/0` manifest takes no dispositions, a non-None value is `schema_invalid`):

- A floor check must be `unconditional` (`floor_check_conditional`): the constitutional floor stays unconditional and in code; a manifest cannot make it conditional.
- An `unconditional` check must have an executed result.
- A `required_when_applicable` check must have an executed result OR a typed disposition `{check_id, predicate, justification, evaluator_id, evaluator_version}` (exactly these members). The predicate must be the check's own (`predicate_mismatch`), the justification must be in that predicate's closed list (`justification_not_allowed`), the evaluator pair must match the manifest check (`evaluator_mismatch`). A disposition for an `unconditional` check is `inapplicable_not_permitted`. A check with both an executed result and a disposition, or two dispositions, is `duplicate_result`; a disposition for an id not in the manifest is `unexpected_check`.
- Absence is never inapplicability: a check with neither is `skipped_mandatory_check`.
- The report still carries no verdict. `/1` adds `inapplicable` to `counts` and, per check, `predicate` (null unless the entry is a disposition; an inapplicable entry has outcome `inapplicable` and the justification code as `reason`). A `failed` or `error` outcome is reported as itself.
- A `not_applicable` executed outcome (reason in the check's list, section 5) and an inapplicable disposition are different: the first is an executed result with a reason over zero items; the second names the predicate that made the check not apply. The disposition is self-asserted by the caller, like `not_applicable`; the module binds it to the exact predicate, a closed justification and the exact evaluator pair, and does not prove it.

### 13.3 Registry side: `/0` cannot express conditional applicability

2.1 refuses a conditional mandatory rule and that stays for profile `ocs-registry-record/0` (the module is unchanged). Consequently the `/1` evaluator accepts a `/0` record only for unconditional checks: a `required_when_applicable` manifest check against a `/0` record is refused with `applicability_unsupported_by_registry` (checked per manifest check, in manifest order, after `registry_rule_missing`), whatever the rule entry says. Until a successor registry profile exists, a `/1` manifest with a conditional check can be validated but cannot complete. What 2.1 would need is proposed (docs only) in [2.1-successor-conditional-applicability.md](2.1-successor-conditional-applicability.md); the rule entries it describes are modelled in the tests through the internal view, and no `/1` registry validator exists.

### 13.5 Closed refusal codes (26)

The 19 of section 4 plus: `unknown_predicate`, `applicability_unsupported_by_registry`, `floor_check_conditional`, `rule_evaluator_mismatch`, `inapplicable_not_permitted`, `predicate_mismatch`, `justification_not_allowed`. The set stays closed (`ManifestRefusal` rejects any other code) and the evaluator stays effect-free: no network, subprocess, file or credential access, and no input mutated.

Order of steps for `/1` (fixed; the first failing step names the refusal): validate manifest (shape, digest, pin, duplicate checks, source, input kind, reason, predicate source, predicate) -> floor shape -> floor subset of the manifest -> floor unconditional -> record validation -> per manifest check: rule missing, applicability unsupported, entries (not required, predicate mismatch, rule evaluator mismatch), evaluator pair listed and qualified -> executed list shape -> dispositions shape -> per executed entry (as section 4) -> per disposition: unexpected, duplicate, not permitted, predicate mismatch, justification, evaluator -> skipped mandatory check.
