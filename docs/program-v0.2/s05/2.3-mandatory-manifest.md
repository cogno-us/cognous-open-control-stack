## Counting the verifier check ids (44 versus 51)

The contract says 44. At `c0b8ba1f` the quoted-literal pattern `"vN.<name>[.<name>]"` over `src/`
matches exactly 44 distinct strings, which is very likely where 44 came from (an inference; the
earlier reading is not in the sources). That number is not the number of check ids:

- 4 of the 44 are not checks: `v2.decisions`, `v2.identity`, `v4.ledger` and `v3.tier` are
  fallback ids used only by `verifier_error(...)` when a whole group raises. They are excluded.
- 11 ids are built by an f-string and have no literal: `v2.journal.{decisions, references,
  attempts, reconciliations, closeouts, refusals, inputs_and_times, journal_mode, vocabulary,
  check_ids, profile}` (`documents.py:138-190`, 131, and the skipped-all list at 336-350). They are
  included.

44 - 4 + 11 = 51 verifier check ids. All are itemized. The 7 `input_read` checks are separate
(58 checks in total). This count differs from the contract's and is reported, not forced.

Conditionality (an open question, see below): the verifier emits many ids only for some inputs (V3
only when a witness or inventory is supplied, V4 only with a ledger, `v2.identity.*` payload ids
only with proposal exports, `v2.profile.*` and `v2.journal.profile` only for records with an opt-in
profile member, `v2.lifecycle.executor_rows` only for lifecycle documents). The manifest follows
the shared specification (every listed check is mandatory, no optional flag), so it lists all of
them; whether each is mandatory for every record class is for the registry rule table's
applicability, not for this data.

## Open disagreements (recorded, not resolved)

1. Refusal input types, Control Plane 5 versus ODES 11. At the pinned revisions the 5-member sets
   match: `RefusalInputVersion.input_type` (`bounded.py:378`) and ODES `changed_input.input_type`
   (`schema.json` 840-858) are the same 5 (`grant`, `policy`, `approval`, `evidence`,
   `role_mapping`). The 11-member set is ODES `resolution_input.input_type` (`schema.json`
   182-196), and Control Plane `ResolutionInput.input_type` (`bounded.py:330-331`) also has the same
   11. So the contract's "5 versus 11" compares two different structures (changed inputs on a
   refusal versus resolution inputs) rather than two readings of one. This is evidence for the
   owner; the manifest takes no side and derives no check from either set.
2. Count: 44 (contract) versus 51 (this manifest); explained above; the contract text is not edited
   here.
3. The 7 mandatory kinds are the verifier's set (a subset of the 11 resolution kinds). The
   Control Plane reads all 7 inside the resolution region (`bounded.py:2267` authority_context,
   2302 role_mapping, 2342 identity, 2355 mandate, 2369 grant via `_read_grant`, 2432 conflict,
   2450 policy), but it holds no table that marks them mandatory; the mandatory marking comes from
   the verifier only.
4. Conditional emission versus "every listed check is mandatory" (above): whether V3, V4, profile
   and lifecycle-only ids belong in a floor for every class is not decided here.
5. Evaluator ids and the version 1 are a naming convention of this candidate, not an existing
   registry of evaluators.
