## Q7: three typed dispositions

- `not_applicable`: a frozen, source-backed applicability predicate establishes that the check is outside the input's scope. In the module this is the `/1` disposition (`dispositions`, closed predicate and justification) and the pre-existing executed `not_applicable` over zero items (closed per-check reason). Neither is inferred.
- `abstained`: the check was applicable and executed but could not establish its substantive result. It is never a pass, is counted in `counts.abstained` (never in `counts.passed`), and its row has `result_established` false. It must carry the verifier's could-not-check reason as non-blank text (for example `input_absent:destination_ledger`, `tier_unavailable:no_items_examined`); the module retains the text and does not interpret it. An entry without it is `schema_invalid`.
- `error`: failed, crashed, timed out or invalid result. Row `result_established` false. The diagnostic cause is optional text (`verifier_error:<ExceptionType>`); a blank cause is `schema_invalid`.

`result_established` is a fact about the row, not a verdict: true for `passed` and `failed`, false for `abstained` and `error`, null for `not_applicable` and for a disposition (a scope statement with no substantive result). A consumer that requires successful verification cannot treat an `abstained` or `error` row as satisfying it. `complete: true` means only that every mandatory check has an accountable outcome; it does not mean substantive success, and the report still holds no verdict, grant, pin selection or activation.

Fit with the closed refusal set, without a verdict: no code is added. `abstained` is an accepted accountable outcome in `/1` and is reported as itself, exactly as `failed` and `error` are. Where the contract cannot distinguish the cases, the module fails closed on existing codes: an outcome that is not one of the typed values (`unknown`, `skipped`, `inapplicable`, a lookalike spelling) is `invalid_outcome`; a not_applicable reason outside the closed list is `not_applicable_reason_not_allowed`; absence is `skipped_mandatory_check`; applicability is never inferred. A `/0` manifest is unchanged: `abstained` is `invalid_outcome` and an `error` with a reason is `schema_invalid`, as before.

Not decided here: the mapping of each verifier could-not-check reason to `abstained` versus a justified `not_applicable` is by the check contract and Qualification, not by this module. The module cannot see the verifier's output, so the caller asserts the typed outcome, as it asserts `not_applicable` today.

## Q8: failure-path surrogates

Both ids are confirmed in the pinned verifier source (revision `c0b8ba1f55b75db787a320f3de0f79342c6f6826`; extract at `/tmp/wk/ver-c0b8`, read-only, which is a source extract without a `.git` directory, so its revision was not re-derived here and rests on the candidate's earlier `git archive` provenance):

- `v1.structure.run-record`: `src/cognous_verify/engine.py` lines 200-216, emitted as a could-not-check `tier_unavailable:run_record_not_parsed` when the run record did not parse, and as `verifier_error(...)` (`verifier_error:<ExceptionType>`, `error` set) when `verify_document` raised.
- `v2.coverage.items-examined`: `engine.py` lines 158-168 with `NO_ITEMS_EXAMINED = "tier_unavailable:no_items_examined"` at line 40, emitted as a could-not-check when nothing is refuted and no non-V1 check confirmed items.

Neither is dropped. They are carried in the new `/1` member `surrogates` (each exactly `check_id`, `failure_condition` from the closed set `no_items_examined` / `run_record_unparsed_or_checker_crash`, and `source_ids`). Rules, all tested with negative controls:

- A surrogate is a conditional manifest check (never unconditional, never a floor check; a floor naming it is `floor_check_conditional`).
- An executed surrogate result is `abstained` or `error` only, with the original trigger retained as non-blank reason text. `passed`, `failed` and `not_applicable` are `invalid_outcome`.
- A surrogate result never discharges another check: each check still needs its own result or disposition.
- The report keeps the surrogate's outcome in the ordinary outcome counts (an error surrogate stays visible in `counts.error`), and adds `counts.surrogate` as a tally over them, plus a per-row `surrogate` naming the failure condition. A surrogate is never counted as a passed execution.
- On a normal run the surrogate may still be closed by its predicate disposition, as before.

The surrogate mapping neither invents coverage nor masks an error in the module's reporting. Whether the mapping is faithful to the verifier is Qualification's to verify. Still open (carried from the candidate): the module does not check the mutual exclusivity of `v1.structure` and `v1.structure.run-record` from the executed list.

## Q9: `input_read.<kind>`

`input_read.<kind>` means the applicable verifier input kind was actually read and accounted for, not merely declared, available, inferred or present in a manifest. The seven ids stay unconditional (`not_applicable_reasons` empty). The module cannot verify that a read happened; it binds the claim to the exact id and evaluator pair, as for every other check, and `passed` is the caller's assertion.

The refuted-V1 wording is recorded as text only:

> The required input was not read because the governing V1 premise was explicitly refuted under the applicable supported profile; the refutation and its evidence are retained.

It is not a justification code, predicate or reason in the data, because no independently accepted applicability rule establishes it. It could become a justified inapplicability claim only where such a rule exists. Until then a refuted-V1 run that did not read a required input reports `abstained` (or `error`) for that `input_read` id, a missing input or unresolved condition, and tests show that the wording as a disposition is `inapplicable_not_permitted` and as a `not_applicable` reason is `not_applicable_reason_not_allowed`. It is not a blanket exemption.

## Q10: `verify_document` crash

A crash is `error`, never `not_applicable`. The candidate data previously carried `checker_crashed_on_run_record` among the justifications of `run_record_parsed_without_checker_crash`, which made a crash recordable as an inapplicability. It is removed, so a crash disposition for `v1.structure` is `justification_not_allowed`, and `not_applicable` with a crash reason is `not_applicable_reason_not_allowed`. The candidate md's own statement that no justification is provided for the crash path is now a decision, not an open point. On the crash path the checks the verifier did not produce are not covered by a crash justification: each needs an `error` outcome (with the diagnostic cause as reason; the surrogate `v1.structure.run-record` carries `verifier_error:<ExceptionType>`), otherwise the run is `skipped_mandatory_check`. Tests show all 50 conditional checks closed as `error` produce `counts.error` 50, `inapplicable` 0, and no row with an established result.

Limitation: the remaining `run_record_not_parsed` justification (not a crash) is a self-asserted source-backed claim like every disposition; the module cannot prove that a caller did not use it to describe a crash. Qualification's independent cases should cover that.

## Open questions for the architect or operator

1. Should any `input_absent:*` could-not-check reason be a justified `not_applicable` predicate (a policy decision), or stay `abstained`? This note assumes `abstained`.
2. Does `run_record_not_parsed` remain an acceptable inapplicability justification for the twelve dependent predicates, given that a not-parsed run cannot establish any result and the surrogate already reports it as `abstained`?
3. Should the module enforce exclusivity of `v1.structure` and `v1.structure.run-record`, and require the surrogate to be present when the corresponding trigger is claimed?
4. Is an `abstained` row's `result_established` false enough, or should the registry or Control Plane consumer state an explicit requirement ("successful verification") that refuses it? That belongs to 2.4 design and is not implemented.
5. Surrogate `source_ids` are only checked to be manifest sources. They are not tied to the target check's own sources or its predicate's sources, so a surrogate could cite an unrelated source. Qualification should verify the mapping.
6. The failure condition `run_record_unparsed_or_checker_crash` merges two triggers (unparsed run record, checker crash) that are distinguished only by uninterpreted reason text (`tier_unavailable:run_record_not_parsed` versus `verifier_error:<ExceptionType>`). This sits with question 3 (exclusivity): should the two be separate failure conditions with a reason check?
7. Cross-reference to question 2: the `run_record_not_parsed` justification leaves the checks of a not-parsed run as `inapplicable`, which sits uneasily with Q7's definition of `not_applicable` as a frozen, source-backed applicability predicate placing a check outside scope. An unparsed run is arguably applicable and unexecuted, which is `abstained` or `error`. Independent review raised this point.
