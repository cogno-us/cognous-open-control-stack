## 2. Declarative data versus typed evaluator code

The profile is data. The evaluator stays typed, versioned code (candidate identity `claim-boundary-scanner`, version 1) and is the only thing that interprets the data. This avoids a second programmable policy interpreter.

| In the data (declarative) | In evaluator code (not in the data) |
|---|---|
| Rule identities and alternatives as ordered element lists | How a match is found, how findings are reported, line attribution |
| Closed element kinds, closed boundary names, closed separator name | The meaning of each element kind (defined in section 3 of this contract and implemented by the evaluator) |
| Literal terms limited to `[a-z0-9]+` | The regular-expression engine or any other matcher |
| Normalization step names, their order and their parameters | The implementation of each step |
| The pre-fold map, dash set and fold table | The Unicode database version and the entity table in use (see section 8) |
| The deferred entries and their provenance | Activation, pinning and the floor |

The data carries no free-form pattern text: a validator can refuse any literal outside `[a-z0-9]+`, any element kind or boundary name outside the closed sets, and any member outside the profile. The historical expressions are shown below only as informative mappings; they are documentation and are never interpreted.

## 3. Element grammar (closed set)

Every alternative is an ordered list of elements evaluated left to right on one normalized view string.

| Kind | Members | Meaning | Informative historical fragment |
|---|---|---|---|
| `boundary` | `name`: `word_boundary` or `no_ascii_alnum_follows` | `word_boundary`: the position separates a Unicode word character from a non-word character or a text edge. `no_ascii_alnum_follows`: the next character, if any, is not `a` to `z` or `0` to `9` (after normalization) | `\b`, `(?![a-z0-9])` |
| `literal` | `value` | exact text | the literal |
| `terms` | `values` (a set, sorted), optional `optional` | exactly one member; with `optional`, zero or one | `(?:a\|b)`, `(?:a\|b)?` |
| `separator` | `name`: `separator_run` | zero or more Unicode whitespace characters (the `\s` class, including line feed, so a separator can cross lines), hyphens or underscores | `[\s\-_]*` |
| `gap` | `max`, `charset`: `any_except_lf`, `lazy` | up to `max` characters other than line feed | `.{0,40}?` |
| `optional` | `elements` | the nested elements or nothing | `(?:...)?` |

A rule matches when any of its alternatives matches anywhere in a view; order is not significant for whether a match exists.

## 4. Record members and determinism

Members of `ocs-scanner-ruleset/0` (exact set; unknown members are refused): `profile`, `schema_version`, `canonical_profile`, `ruleset_id`, `status`, `evaluator`, `normalization`, `views`, `markup`, `rules`, `deferred`, `compatibility`, `digest`.

- Canonical form and digest: the 2.1 profile `rfc8785-jcs` (no floats) and `sha256:` over the record without its `digest` member, computed with the same function as 2.1 (`record_digest`).
- Set-valued arrays (term values, known elements, extra dashes, markdown marks) are sorted by code point. Sequence-valued arrays keep their order and the order is part of the meaning (elements, normalization order, views). Rules are sorted by `rule_id` and alternatives by `id`. Fold table keys are single code points and unique.
- Normalization order, exactly: `html_entities`, `escaped_whitespace`, `pre_fold`, `nfkc`, then per character `nfd`, `drop_invisible`, `casefold`, `dash_fold`, `table`. Reordering changes behavior (for example, the pre-fold must precede NFKC because NFKC maps U+03F9 to a capital sigma; escaped whitespace must be read before backslashes are dropped, otherwise `"certified\n"` is hidden).
- Views: `stripped` and `unstripped` (each followed by an underscore-removed view) and `comment_text`, reported as hidden-source only when the same line and rule has no visible match.
- The fold table has 78 keys. The key `ё` is declared but unreachable (NFD removes the mark first); its effective result equals its declared target, and the data says so. All other keys are reachable (checked in `tests/test_scanner_ruleset_candidate.py`).

### How the 2.1 registry record references it (no 2.1 change)

The closed 2.1 shape needs no new member. A record lists `ocs-scanner-ruleset/0@sha256:<digest>` in `source_refs`, and each scanner rule entry names that string as its `source_ref`. The illustrative record uses class `scanner`, profile `claim-boundary`, failure disposition `hold`, `fail_closed` for missing input, evaluator `claim-boundary-scanner` version 1, status `advisory` (the status of scanner rules is a later decision, not made here), and no entry for the deferred alternative.

Two consequences are recorded rather than hidden. First, 2.1 does not parse or verify that reference string; the consumer that loads the ruleset must verify that the digest of the data equals the digest in the reference, and a typed reference member would need a new 2.1 profile version (not proposed here). Second, 2.1 correctly refuses the illustrative record: `validate_record` returns `unqualified_evaluator` because the evaluator has no qualification reference. That refusal is tested and is the intended behavior until Qualification qualifies an evaluator.

## 6. Terminator (D-2)

Candidate semantics: the first, second and third `production-ready` alternatives end with `no_ascii_alnum_follows`.

What is true by position: for the same normalized string and the same position, `\b` after an ASCII letter accepts only when the next character is not a word character, and `(?![a-z0-9])` accepts when the next character is not an ASCII letter or digit. So at one position the lookahead accepts everything `\b` accepts and also accepts a following underscore and any following non-ASCII letter, digit or ideograph.

What is not true end to end: the scanners differ in more than the terminator, and the direction can reverse. In the 105 measured cases (35 tails on each of three alternatives; [boundary-cases.json](../../../fixtures/scanner-differential/boundary-cases.json)), the verifier and ergonomics scanners disagree on 40. Attribution:

- Terminator: six tail classes on alternatives A and B, where the verifier matches and ergonomics does not: underscore then a letter, underscore at end, an unmapped Cyrillic letter, an unmapped Greek letter, a CJK ideograph, an Arabic-indic digit.
- Backslash handling: a literal backslash-n after the phrase (T-01): the verifier matches, ergonomics does not.
- Markup: `<b>x</b>` after the phrase: ergonomics matches and the verifier does not, which is the opposite direction. The verifier strips `<b>` and sees `readyx`; ergonomics also matches a second view with no tag stripping (the N3 dual view), which sees `ready<`.
- Alternative C is absent from the ergonomics scanner (S-01), so most C cases differ for that reason.

Candidate expectations (proposals; Qualification freezes any expectation): positives include end of text, a space, ASCII punctuation, `_`, a following unmapped non-ASCII letter, CJK, an Arabic-indic digit, a combining mark directly after the last letter or before punctuation. Negatives include an ASCII digit, ASCII letters in either case, a Cyrillic letter that the table maps to a Latin letter, fullwidth digits and letters (NFKC gives ASCII), a precomposed accented letter (the base letter remains), and a combining mark, zero-width joiner or soft hyphen followed by a letter (the ignorable character is dropped and the letter then continues the word).

**Open question O-1 for the operator or Qualification (not decided here):** the candidate semantics accept a following underscore and a following non-ASCII letter or digit (`ready_x`, `ready_`, `readyя`, `readyλ`, `ready中`, `ready٣`). That is how the verifier behaves today and is what "adopt the verifier's terminator semantics" yields; if those cases should instead be treated as the word continuing, the boundary name would be a different, stricter one (equal to `word_boundary` for these cases) and all six tail classes above would flip. The data names the boundary so either choice is a one-word change in a future version.

My earlier statement that this terminator is "broader, so it only adds matches" is withdrawn as an end-to-end claim; see the addendum in the tree-check record.

## 8. Compatibility assumptions and limits

- The 287-match result supports compatibility on the measured hub tree at the measured revision, not equivalence across all inputs or later revisions.
- Evaluator and data versions are coupled: entity decoding follows the Python standard library `html.unescape` table, and NFKC, NFD, casefold and category results depend on the Unicode database of the running interpreter. The data cannot pin either. Proposed (not added here): the evaluator qualification records the interpreter and Unicode data version, and a version change is a requalification event. The checks in this repository run on the interpreter versions of the existing CI.
- The analysis model is not an evaluator. A test-local reference reading of the data (in `tests/test_scanner_ruleset_candidate.py`) checks that the data reproduces the model's rules on the 178-case corpus and the 105 boundary cases; it is not a scanner and is wired into no gate.
- **Open question O-2 (entities without a terminating semicolon):** the verifier decodes entities with `html.unescape` on the whole line, which also decodes entities without a trailing semicolon (`production&nbspready`, `&#99ertified`). The ergonomics scanner, the analysis model and therefore this candidate decode only semicolon-terminated entities, so under the candidate the verifier would lose those detections. This was not covered by the corpus, the boundary cases or the 287-match result; six cases are recorded in `entity_cases` of the boundary-cases file. Decision for the operator: keep semicolon-only (as modeled) or adopt the verifier's behavior, which is a superset for the first three kinds and would be the compatibility-preserving choice.
- The hub scanner (N5) is deferred and not represented. The file-scope question (S-14) is undetermined and not represented.
- Alternatives S1a and S1b (verifier shape) and S2 (ergonomics shape) are all adopted per N1 and S-03; adopting S1a in the Ergonomics repository matches its own prose at `docs/development.md:50` (D-4).
