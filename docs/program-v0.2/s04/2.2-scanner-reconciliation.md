# Step 2.2: scanner reconciliation (classification before extraction)

**Candidate analysis, non-authorizing; no scanner behavior is changed by this record.** Authorized by the [M0 decision record](../m0-decision-record.md) (ADR-P02: reconcile all three copies, classify differences, then define one normative behavior; any behavior change returns to the operator). Release and production remain on HOLD. No locked component is changed; the verifier copy stays an M2 exclusion.

Method: `tools/scanner_differential.py` loads the pure text functions of the three copies and runs them on a frozen synthetic corpus (`fixtures/scanner-differential/corpus.json`, 178 strings). Results: [2.2-differential-results.json](2.2-differential-results.json). It has no effect of its own (no scanner CLI, no tree scan, no file writes, no network), but it imports the scanners' modules, so module-level code of the pinned checkouts runs; bytecode writing is disabled. Sources: verifier `c0b8ba1f` and ergonomics `bea582b` `scripts/check_claim_boundaries.py`, hub `tools/collateral_evidence_snapshot.py` at `a3c7971`.

Classification meaning: **deliberate** (source or commit message states the intent), **omission** (one copy lacks something the other copy's stated intent covers), **defect** (a copy fails its own stated purpose on a measured input), **undetermined** (no stated intent; the owner decides). Classifications are proposals from source and commit messages; the owners' intent was not asked. The scanners are accident-prevention lint, not a security boundary.

## 1. What was measured

- The verifier and ergonomics scripts are different implementations, not copies. They share rule names and the lookalike idea but differ in folding order, markup handling and rule bodies. On the corpus they disagree on 31 inputs; no input has both copies matching the same rule on different lines (line attribution disagreements all follow rule disagreements).
- Lookalike tables: verifier 76 keys, ergonomics 77, hub 67. The 73 keys shared by verifier and ergonomics map identically (no value conflicts). Verifier-only keys: σ ё ꞯ. Ergonomics-only keys: ɔ ɛ ς ϲ.
- The hub scanner is a different mechanism (a negation-aware wording check of collateral strings with its own term list), not a third copy of the rule set; it shares only the fold idea. On a single-character fold probe the three differ on 31 of 96 characters probed.
- No false-positive baseline exists; none was measured here.

Consequence of N1 to N4: each is expected to add findings, but that is not demonstrated (a reordered fold pipeline could remove a match in an edge case), so the normative corpus must be run on both directions. That run is not done here; it executes the scanners' CLI over repository trees and needs your approval and the repository access for it.

## 4. What this does not do

It changes no scanner and no repository other than adding the harness, corpus and records in the hub. It selects no rule family (the M1 family decision stands: scanner family for the two unlocked consumers, the verifier an M2 exclusion). The verifier-side defects S-05 and S-12 and the ergonomics-side S-07 are findings for the owners; fixing the verifier is a locked-component change (F3) and is not proposed here. It writes no registry rules; the crosswalk follows the N decisions. Qualification owns the independent corpus and expectations for A2.
