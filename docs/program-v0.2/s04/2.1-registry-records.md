# Step 2.1 implementation note: versioned rule records and bounded store

**Candidate implementation, non-authorizing.** Authorized by the [M0 decision record](../m0-decision-record.md) (step 2.1, scope in section 3). It is engineering evidence only: it does not qualify itself, activates nothing, selects no pin, and has no effect surface. No locked component is changed. Release and production remain on HOLD.

Files: `tools/registry_records.py` (standard library only) and `tests/test_registry_records.py`. Contract: [1.3](../s02/contracts/1.3-registry-r0.md) sections 3 to 5.

## What it does

| Part | Behavior |
|---|---|
| Canonical JSON | RFC 8785 form for objects, arrays, strings, booleans, null and safe integers; keys sorted by UTF-16 code unit; floats, non-finite numbers, duplicate keys and lone surrogates refused. Profile name `rfc8785-jcs` (ADR-P01: new commitments use JCS; the legacy form is a different named profile and is not accepted here) |
| Record digest | `sha256:` over the canonical form of the record without its own `digest` member |
| Validation | Exact members, typed positions (a boolean or null is never an integer), closed status, disposition and missing-input vocabularies; missing input must fail closed; referential integrity of reason codes, source references and evaluators; duplicate or shadowed rules, unknown or unqualified evaluators, a digest that differs from the canonical digest, and a digest that differs from a supplied pin are refused |
| Floor | The caller passes the mandatory rule ids explicitly (no default). A mandatory rule must be present, `required`, and unconditional. A conditional applicability for a mandatory rule is refused because no source predicate is proven by this code |
| Succession | Epoch strictly increases; the predecessor must be the latest digest; the first record has no predecessor |
| Store | Append-only directory, exclusive create, read-only files, explicit count and size bounds, file name bound to epoch and digest, every load re-validated; symlinks, unexpected names, non-strict JSON and tampered bytes refused. Publication is not activation: there is no active-record notion here |

Refusals are typed from a closed code set and change nothing.

## What it does not do (claim limits)

- It does not authenticate. A pin is a digest held outside the store; the claim is "pinned and immutable", not "signed". An asserted `issuer` is a name.
- It does not activate a rule set, resolve a mandatory manifest, bind a digest into any decision, or touch the Control Plane. Those are steps 2.3 and 2.4 and the F3 packages, each separately authorized.
- It carries no real rule content. The mandatory rule ids, the rule table for the scanner family and the evaluator registry belong to steps 2.2 and 2.3.
- Field names are candidates for the wire-name freeze; `ocs-registry-record/0` is not a frozen schema. A change to a name before independent qualification starts is expected and cheap; after it, it needs a new profile identifier.
- Not independently qualified. The 33 developer tests were mutation-checked (removing the digest check, the mandatory-required check, the epoch check, the pin check or the shadowing check each fails at least one test), which shows the tests exercise those rules, not that the rules are sufficient.
- Qualification owns the independent expectations for A1 (mechanism) and A2 (migration). None is written or edited here.
