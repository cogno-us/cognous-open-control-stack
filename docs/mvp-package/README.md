## Candidate manifest: how to validate it, and what it does not claim

[candidate-manifest.json](candidate-manifest.json) records one exact candidate tuple so that it can be validated independently: the component revisions (full 40-hex), the Python 3.13 hash-locked dependency file, the Qualification source and draft references, the supported configuration (profile document, ingress tree digest, capture script hash), the registry catalogue manifest digest and the state of evidence and test-run identities. Status is UNQUALIFIED and provisional. Release, publication and production are HOLD. The historical Hub component lock (`component-lock.json`) is stale and does not describe this tuple; it is recorded by hash only so that a change to it is detected.

How to validate (standard library only, from the repository root):

```bash
python -I tools/mvp_candidate_manifest/validate_candidate_manifest.py            # offline, deterministic
python -I tools/mvp_candidate_manifest/validate_candidate_manifest.py --online   # also checks each revision is an ancestor of its main (needs the gh CLI)
python -I tools/mvp_candidate_manifest/validate_candidate_manifest.py --manifest PATH --repo-root DIR
PYTHONPATH=".:src" python -m pytest -q tests/test_mvp_candidate_manifest.py
```

The validator checks: required fields and schema; every revision is a full 40-hex; no duplicate component; the Verifier pin is not 39d46b49, which is listed only as a later documentation revision that is not implicitly covered; the ingress tree digest is recomputed from `tools/mvp_ingress/*.py` (sha256 over `basename NUL file-sha256 NEWLINE` lines, sorted by base name); the hub lock, dependency lock, profile document, boundary document and capture script hashes match the files; the pinned dependency versions appear in the lock file; the catalogue digest status is one of superseded-pending, superseded or current and is consistent with its successor field; evidence and test-run identities are explicitly "not yet produced" and the candidate commitment is null; and no verdict, pass, qualified, frozen, accepted or assurance wording appears. It exits 1 on any problem and gives no verdict about the candidate. Passing it means only that the manifest agrees with this checkout.

Expected tuple: the validator embeds the Architect tuple (component repository names and full revisions for the seven pinned components, the registry digest, the ingress tree id, file list and digest) and fails on any mismatch. `--expect-tuple FILE` takes JSON such as `{"components": {"hub": {"repository": "...", "revision": "<40-hex>"}}, "registry_digest": "sha256:..."}` and merges it over the embedded values, for example to pin the hub revision. A successor manifest updates the embedded expected tuple in a reviewed change to the validator; it is never edited silently. The hub revision is embedded too (the hub provenance revision is hub main c897266b, the merge of PR #232; later hub commits that do not touch `tools/mvp_ingress` or `tools/mvp_env_record` do not change this candidate). When the catalogue status is superseded, `--expect-tuple` with `successor_registry_digest` makes the validator require a matching `successor_value`; without it the superseded state accepts any well-formed successor.

Ingress tree: the manifest records the git tree id of `tools/mvp_ingress` at the hub revision and the exact 8-file list (including BOUNDARY.md and launch.py). The validator recomputes both locally and refuses any extra file, subpackage, symlink or non-.py file there (there is no exception: a `__pycache__` directory there is refused too, because a crafted timestamp pyc could otherwise run unreviewed code; run with `python -B` or `PYTHONDONTWRITEBYTECODE=1`). The digest covers direct `*.py` files only; a committed package shadowing `proposal.py` would pass the digest alone but is refused by the file-list and tree-id checks. NC4-03 AST pins require CPython 3.13. Hub-root, current-directory, `PYTHONPATH`, user-site and planted-bytecode import paths are mitigated only for the supported launcher form `python -I tools/mvp_ingress/launch.py ... --allow-uid UID` (see BOUNDARY.md for precise coverage; installed packages are trusted except the checked Control Plane / Runtime modules); the former `python -m tools.mvp_ingress.server` form, code running as an allowed uid, the ingress uid or root, tampered interpreter, standard library or site-packages, and the host (Yama) are not covered and unclaimed.

Wording guard: text is lowercased with whitespace normalized; verdict-style terms (pass, fail, qualified, frozen, accepted, certified, production ready and similar) are allowed only directly after an explicit negation such as "not", "no" or "does not claim", and boolean keys such as `qualified`, `frozen`, `accepted` or `certified` set to true are refused anywhere. Malformed shapes produce INVALID with exit 1, and `--online` without `gh` prints a clean error.
