## A1: design (NC2-07, scenario `nc_process_kill`)
- Victim = real subprocess (`python _killharness.py victim ...`) wiring the pinned tuple via `conftest`, building `_chain.Ctx` on a durable on-disk work dir (CP `run.json` + SQLite WAL db), provisioning the claim, then calling the pinned `AtomicLocalControlPlaneExecutor.execute`. The pinned destination's documented no-op hook `_transaction_stage` (Runtime `local_authority_effect.py:778`, "deterministic qualification subclasses") is overridden in a subclass ONLY to print `READY <seam> <pid>` on the stdout pipe and block (sleep loop). It injects no fault; `simulate=` is never passed; the target does not exit itself.
- Parent blocks on the pipe (`select`) until READY (timeout 180 s, only able to cause BLOCKED/FAIL, never pass), records pid/proc evidence and file hashes, `os.kill(pid, SIGKILL)`, waits, records `returncode == -9`, `/proc/<pid>` gone, hashes the on-disk store BEFORE any open (WAL file present), and copies it as an artifact.
- Observer = a second fresh subprocess (new pid) that reopens the same persisted CP record (`BoundedRecordStore`) and the same SQLite file (this open performs SQLite recovery), reads tables via independent `mode=ro` connections, calls `reconcile_claim`, presents the claim twice through the executor, reads back after each step.
- Determinism: the kill happens at a barrier, no timing reliance. One thing I found: the victim's `/proc/<pid>/stat` state at kill time is R or S depending on microseconds (my first test asserted S and failed once); it is recorded as evidence only and not asserted.
- Seams (3, all deterministic): `after_begin`, `after_effect_insert_before_commit` (kill inside the open write transaction), `after_commit` (durable COMMIT, no acknowledgement can reach the caller). All three made deterministic. `before_begin` not included (nothing written; adds nothing); `before_failure_record` is a seam of the frozen F5b reference (historical `test_scn_c08`), NOT of the pinned route B executor: no such stage exists, so it is not claimed.
- Required semantics = the pinned code's contract (OBSERVED, not invented): pre-COMMIT seams: SQLite rolls back; 0 effect/attempt/receipt/operation rows, budget 0, claim `issued`; `reconcile_claim` -> `hold` / `no_durable_effect_for_claim` / `retry_eligible False`. NOTHING recovers automatically: a new `execute` with the still-issued claim delivers the effect exactly once (`executed`), a further presentation is `denied` ("execution claim is not usable"), 1 effect. Post-COMMIT seam: 1 effect, 1 attempt, 1 receipt, 1 operation row, claim `consumed`, reconcile `applied` (same effect id, `retry_eligible False`), re-presentation `denied`, not attempted, not acknowledged; the caller never receives an acknowledgement (the pinned code cannot deliver one to a dead process). Effect count never exceeds 1.
- Wording guard (INFERENCE): the row proves process-death behaviour of the destination state and reconcile/refusal, not "automatic recovery"; the claim text must not say recovery of the acknowledgement or automatic retry. Power loss, OS crash, kill during claim provisioning, Replay/Pack/Verifier steps, CP process kill are not exercised (module docstring says so).
