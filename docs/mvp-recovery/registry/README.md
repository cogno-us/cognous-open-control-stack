# Layered governance catalogue (informational)

DRAFT. Non-authorizing: every record carries `authority: none` and `non_authorizing: true`. The catalogue activates nothing, selects no pin, executes no rule, scenario or test, and makes no qualification statement. Release and production remain on HOLD. Population of this catalogue is outside the MVP critical path; it does not change the fixed MVP profile.

This directory holds two catalogues. The root (`manifest.json`, `rules/`, ...) is a small SYNTHETIC SAMPLE (`synthetic_sample: true`) that exercises every schema and check. `catalogue-v0.1/` is the catalogue assembled from the real partition outputs (`synthetic_sample: false`) in the compact layout described below, with its own manifest, schema copy (byte-identical to `schemas/`, enforced) and reports.

## Layers

| Layer | Directory | Schema | Identity | Meaning |
|---|---|---|---|---|
| L1 rules | `rules/` | `schemas/rules.schema.json` | `R-` id | Catalogue profile entry that references a rule by identity plus digest. For rules held in an `ocs-registry-record/0` record it carries `registry_id`, `record_digest`, `rule_id`, `version` and the `rule_digest` of the rule row. |
| L2 scenarios | `scenarios/` | `scenarios.schema.json` | `S-` id | Logical scenario with verbatim expected outcome, polarity, temporal/recovery flag and a `scenario_class` (`logical`, `suite_level_acceptance`, `adversarial_or_unexecuted_spec`). |
| L3 tests | `tests/` | `tests.schema.json` | `T-` id | Test implementation; parametrized instances are counted, never separate entries. |
| L4 fixtures | `fixtures/` | `fixtures.schema.json` | `F-` id | Reference plus content digest and locations; bytes are never copied. |
| L5 evidence index | `evidence-index/` | `evidence.schema.json` | evidence digest | Execution evidence, outside the rule catalogue. Verdicts are quoted verbatim and `current_qualification_effect` is always `none`. Source and artifact commitments are mandatory. |
| L6 coverage | `reports/` | `coverage.schema.json` | subject id | Derived projection (see below). |
| crosswalk | `crosswalk/` | `crosswalk.schema.json` | `(raw_set, raw_index)` | One row per raw record. A partition that reads several raw files whose indexes overlap is kept as several raw sets (A, A2; C, C2, C3). |
| lineage sets | `lineage-sets/` | `lineage_sets.schema.json` | `L-` id | Named append-only logs of historical revision records (amendment log, refreeze log). Not a rule, scenario or test. |

Shapes the real partitions need: a scenario defined by a fixture file is co-registered (`annotations.co_registered` on the fixture's crosswalk row) and needs no own CANONICAL row; a fixture that is only named by a source and has no raw record is `annotations.reference_only`; `alias_candidates` lists same-layer entries that were flagged as possibly equal and NOT merged (a merge needs a stated basis, kept in `annotations.merged_from`); `related_refs` are same-layer links from the relationship pass. `SOURCE_ONLY_ARTIFACT` is only for non-canonical tiers (`RULE_ADJACENT`); a canonical, revision or evidence tier record that cannot be placed is `UNRESOLVED` with a reason. A non-`unresolved` `mvp_applicability` carries a `basis_id` and a `source_ref` (that the named source really says so cannot be mechanised).

Registry-record contracts are reused, not changed. `tools/registry_records.py`, the 2.1 note and the R0 contract are untouched; catalogue metadata sits in this separate non-authorizing profile. A registry record referenced by the catalogue is kept under `rules/registry-records/`, is checked with `validate_record`, and must contain advisory rules only. Hashing follows `tools/registry_records.py`: `sha256` over RFC 8785 canonical JSON (a record's `digest` excludes its own member). Partition hashes are `sha256` of the file bytes.

Every entry has `source`, `native_ids`, `aliases` (every merged alias is retained), `raw_refs`, `lineage` (historical revisions, never overwritten), `annotations` (verbatim carried fields; no authority keys), `relationships`, `release_scope` (`v0_1|post_v0_1|unknown`) and an explicit `mvp_applicability {value, reason}` with value one of `mvp_fixed | other_supported_historical_profile | requires_unavailable_component | needs_migration | historical_only | unresolved`. Rules also carry `normative_type` (`constitutional_floor | mandatory | conditional | advisory | principle | reason_code_or_refusal_vocabulary | validator_rule | requirement_row | decision | unknown`) and `adoption_status`; only adopted CR-001..CR-035 identities may be a `constitutional_floor`.

## Relationship provenance (R1)

Each reference (rule to scenario, scenario to test, test to evidence, and so on) has one relationship record: `SOURCE_STATED` (exact repo, revision, location), `DERIVED` (method, supporting refs, confidence class `high|medium|low|heuristic`, no source claim) or `UNRESOLVED` (names the missing evidence). The flags `establishes_enforcement`, `establishes_test_coverage` and `establishes_qualification` are always `false`. An `UNRESOLVED:` target cannot carry another provenance.

## Coverage (R2) and denominators (R3)

Coverage rows hold four separate assessments, none inferred from another: `catalogue_completeness`, `implementation_coverage`, `test_coverage`, `independent_qualification`. A `DERIVED` link is only a candidate (`derived_candidate_only`). `implemented` needs a source-stated test link; `tested` needs a source-stated run-result evidence link; `independently_qualified` needs a source-stated independent qualification record, which a run result or historical verdict never is. `excluded_or_unsupported` follows `requires_unavailable_component` or `historical_only`. The validator recomputes every row and refuses any difference.

`tools/generate_reports.py` writes `reports/generated/` (not hashed by the manifest because it names the manifest): the Catalogue Integrity Report, the Governance Coverage Report and the Denominator Report, each naming the exact manifest digest and source revisions. The Denominator Report keeps ten denominators apart and has no headline scenario count: rules by normative type, logical scenarios, suite-level acceptance scenarios, adversarial or unexecuted specifications, test implementations, parametrized instances, fixtures, historical execution records, distinct execution identities, historical verdicts.

## Size policy, compact layout and regeneration

Written as plain JSON the real catalogue is far over the size policy (about 140 MB, files up to 10 MB), so it is not committed in that form (the compact catalogue is about 42 MB, no file over 4 MB). `--layout compact` (see `build_registry.py`) commits L1-L4, the lineage sets, the crosswalk (index form), the evidence index (index form) and the coverage rows, all in a lossless interned-strings and shape-table encoding (`ocs-interned-shapes/0`, decoded by the validator), plus the manifest with the `sha256` of every partition and of every schema file. Three bulky layers stay out of the repository as content-addressed artifacts that the manifest describes (`external_artifacts`: path, `sha256` of the uncompressed content, record count, bytes and `committed`; a committed artifact is deterministic gzip, level 9, mtime 0, no embedded name, and its entry also records `gzip_sha256`, `gzip_bytes` and `compression`): `evidence_records` (full evidence records, verdict text included), `crosswalk_rows` (full rows with `path`, `native_id` and all annotations) and `relationship_rows` (the G3 rows each embedded relationship names by `row_id`). The committed index entries are derived from the full ones by a deterministic function in the validator (`slim_evidence`, `slim_crosswalk`), and the validator verifies the artifacts byte for byte against the index: committed `.json.gz` artifacts next to the manifest are checked automatically (the gzip file against `gzip_sha256`, the decompressed content, capped at the recorded size, against `sha256`); uncommitted artifacts are checked only with `--artifacts DIR`, otherwise the validator says so. The decompressed content digest is authoritative. The gzip bytes depend on the zlib build: when `gzip_sha256` differs but the decompressed content matches `sha256`, the validator passes and prints an explicit `WARNING artifact ...` line (never silent); any change to the content still fails.

Regeneration is deterministic: `manifest.regeneration` pins the loader command, the partition names, the number of input files and the `sha256` over every input file read (plus one per input directory). Running the loader on identical inputs and tool files reproduces every committed file and every artifact byte for byte.

The generated reports are not hashed by the manifest because they name the manifest digest; `generate_reports.py --check` (run by the tests for the sample) is the freshness check and refuses a stale file.

## Manifest

`manifest.json` (`ocs-catalogue-manifest/0`): registry version, schema versions, source inventory commitments (raw record count and an inventory digest per raw set, with source repo revisions), per-partition `sha256`, record count and key range, per-layer counts, `unresolved_accounting`, registry-record pins, generation-tool revision (hashes of the generator and validator) and completeness limitations. Partitions are split by layer, source family (from the id) and ID range, in files of at most 200 records.

The validator refuses (codes in brackets): a raw record missing or repeated in the crosswalk, or a changed raw digest [crosswalk_*, inventory_commitment_mismatch]; duplicate ids per namespace [duplicate_id, namespace_mismatch]; unresolved typed references [unresolved_reference]; rule/scenario links that disagree [link_not_bidirectional]; evidence without source or artifact commitments [evidence_commitment_missing]; dropped aliases or lineage [alias_not_retained, revision_not_retained]; overwritten or removed history against `--previous` [historical_*]; unclassified MVP applicability [record_schema]; evidence presented as a rule [evidence_as_rule]; coverage not derivable from explicit links [coverage_inferred]; any `authority` other than `none` [authority_promotion]; partition hash, count, range or manifest digest mismatch; missing, orphaned or mis-provenanced relationships and promoted unresolved links [relationship_*, unresolved_promoted]; unresolved counts that differ from the manifest [unresolved_accounting_mismatch].

Additional refusals: schema files that differ from the manifest pins or from the validator's own copy [schema_not_pinned]; a canonical-tier record made source-only [crosswalk_tier_mismatch]; alias candidates and related refs without provenance, with unresolved targets or with a flipped flag [relationship_*, unresolved_reference]; `unrecorded` artifact paths and `SOURCE_STATED` links with an unrecorded revision [evidence_commitment_missing, relationship_provenance]; duplicate reference targets [duplicate_ref]; identifiers that are not printable ASCII without whitespace [id_form]; a merge without a retained alias and stated basis [merge_basis_missing]; lineage that points at no crosswalk row [lineage_without_crosswalk_row]; an applicability value without basis [mvp_basis_missing]; forbidden annotation keys, matched case-insensitively [authority_promotion]; `--previous`: the previous registry must validate itself [previous_invalid] and a change of `scenario_class`, `normative_type`, `adoption_status`, `mvp_applicability` or `release_scope` needs a recorded transition `{field, from, to, previous_digest, basis}` in `annotations.attribute_transitions` [attribute_changed_without_transition]; artifact problems [artifact_*].

Standing refusals against the catalogue itself [named codes]: a derived or unresolved link reported as implemented, tested or independently qualified coverage, or a run result used as a qualification record [derived_reported_as_coverage, unresolved_became_established, unresolved_hidden_from_completeness]; a historical record with a current effect, or an applicability basis that names a run result [historical_result_assigned_to_current]; a differential suite with instance rows counted as a logical scenario, instances, collected nodes or executions made entries [suite_rows_counted_as_logical, instances_counted_as_unique]; a code-registry entry typed as a normative rule, or a 0.2 entry absorbing a 0.1 identity [normative_vocabulary_conflated, registry_versions_merged]; committed denominators or per-layer unresolved counts that differ from the recomputed ones [denominator_mismatch, unresolved_accounting_mismatch]. `source_reference_refs` record inbound links from source-only raw records as `SR:<partition>:<raw digest>`; each must name a `SOURCE_ONLY_ARTIFACT` crosswalk row and carries its own relationship record.

The artifacts are compared field by field with the embedded copies: relationship rows (provenance, method, confidence, supporting refs, source, `missing_evidence`, every `establishes_*` flag and the endpoints), evidence records (the whole index entry, path included) and crosswalk rows (the native id against the entry it names), each also checked against the record schemas, with duplicate keys, duplicate row ids and unaccounted orphan rows refused [artifact_index_mismatch, artifact_row_schema, artifact_duplicate_key, artifact_orphan_row]. A relationship row that no entry embeds must be accounted for: instance level, no catalogue endpoint, a revision link, or an endpoint pair already recorded. A crosswalk row's `path` has no committed copy to compare (the raw digest binds the raw content, not its path), so a changed path in the crosswalk artifact is not detected.

Source revisions: the validator pins the tag commits of the twelve repositories and the two named post-tag heads inside its own bytes (`PINNED_TAG_COMMITS`, `PINNED_POST_TAG`); a manifest that names a pinned repository must cite only those hashes or `unrecorded` [source_revision_not_pinned], cannot claim `synthetic_sample` [synthetic_flag_on_real_catalogue], and no entry, location or evidence record may cite a `multi:` pseudo-repository [pseudo_repo]. In a catalogue that names pinned repositories every entry, `locations` item, lineage set and evidence record must also cite a pinned repository with a pinned hash, or exactly `unrecorded` [source_revision_not_pinned]. A fixture that names none of the pinned repositories is outside this check.

MVP-linked overlay (Architect MVP decisions Q8, 2026-10, registry applicability; a point-in-time ruling reported to the registry worker and not retained in this repository, not the hub Q8 on the trusted synthetic resolver; the architect Round 3 ruling Q6, also reported and not retained, is the other basis: `mvp_fixed` only where the exact rule identity and an exercised source-backed path are confirmed): `overlays/mvp-linked-q8.json` is a small, deterministic loader input (`load_partitions.py --overlay FILE`); its path and sha256 are pinned in `manifest.regeneration` (`inputs.overlays` and the command), and the validator refuses a committed overlay file that differs from the pin, an `OVERLAY` row that is not an overlay item (or a missing one), an extra link of an overlay relation kind from any other rule, the basis `MB-ARCH-MVP-ROW` on a rule that has no overlay link or is not listed, and an alias equal to another rule's native id [overlay_pin_mismatch, overlay_rows_mismatch, mvp_basis_misapplied, alias_collides_native_id]. Each of its nine items names one existing entry by catalogue id and by the exact identity it must carry (native id, source repository, source path, normative type); the loader refuses the load on any mismatch, on a target that is not an MVP expectation-row scenario (`mvp_fixed` on basis `MB-MVPCHAIN-ROW`), or on a duplicate link. It adds G3-shaped rows of partition `OVERLAY` and embedded relationship records in both directions (`scenario_refs` on the entry, `rule_refs` on the scenario). Nothing is merged, renamed or removed: the three `journal_check_reused` records and the two `decision_result_inconsistent` records stay distinct entries with their source-specific identities. `journal_check_reused` (VER-02) and `decision_result_inconsistent` (NC5-04) are `DERIVED` rule-to-scenario links (`rule->scenario`, relation `mvp_requirement_named_by_row`). Only the Verifier `decision_result_inconsistent` rule (NC5-04, the row asserts the finding present) becomes `mvp_fixed`, on basis `MB-ARCH-MVP-ROW`, which needs an exercised source-backed path. The Verifier `journal_check_reused` rule (VER-02: No Verifier finding with code journal_check_reused) is a negative control (`not_contains`: absence of the finding, not the rule seen to fire), so after architect Round 6 it stays unresolved with a `DERIVED` low-confidence association link (it was `mvp_fixed` in the first Q8 build); the replay-bundle and ODES `journal_check_reused` records and the ODES `decision_result_inconsistent` record keep their distinct identities and their `DERIVED` low-confidence links to the MVP row as association only, with unresolved applicability, because neither equivalence nor an exercised enforcement path is established. The `mvp_fixed` basis rests on the proposed (not frozen) expectations and links v0.1 rules to post_v0_1 scenarios. `SCN-C08` links NC2-01 to NC2-05 (same family and executor-level scenario); NC2-06 (supported-ingress evidence, first present at v6) is deliberately not linked and the link note says so. The supporting references cite the v3 rows and the v6 reference the scenario records cite, and state that the linked rows have identical text in both except NC4-03 (title and predicate differ). `scenario_notes` of the overlay annotate an MVP expectation-row scenario (`annotations.mvp_overlay_note`) without editing its quoted text: the NC4-03 record keeps the v6 predicate with ingress digest ea37100d... byte-faithful, and the note records that the Qualification v7 draft (pull request 225, proposed, not adopted) pins ingress digest 0c0e2cf6... (hub c897266b, `tools/mvp_ingress` tree 656b506d...); the validator requires the annotations to equal the pinned notes [overlay_note_mismatch]. Relationship rows carry `claim_status` from a closed set (`candidate_link_only_non_authorizing`) [artifact_row_schema]. `SCN-C07`, `SCN-C08`, `SCN-C09` and `SCN-D09` are requirement rows: they carry `DERIVED` typed links `requirement_row->scenario` (relation `mvp_requirement_row_link`, medium confidence, method family and name correspondence) to the MVP expectation rows of their control family; `docs/mvp-recovery/critical-path.md` line 67 names only the SCN family labels, not the NC rows, so the row mapping is not source-stated. `SCN-D09` is limited to route B (`architect-rulings-3-and-known-limitations.md` section 5). They are never `mvp_fixed` as rules [requirement_row_mvp_fixed, mvp_link_untyped]. The manifest denominators carry `rule_headline` (mvp_fixed rules by normative type, requirement rows reported apart). A link establishes no enforcement, test coverage or qualification (association only; not satisfied, enforced, tested or qualified); every other entry keeps its unresolved applicability, which is not evidence that a requirement is unimplemented and not a coverage claim.

Unembedded G3 relationship rows: a relationship row that no entry embeds belongs to exactly one class, and each class has a signature that the validator checks row by row (a row that fits none, or fails its class, is refused [artifact_orphan_row, artifact_row_signature]). `instance`: a derived `differential_instance->scenario` membership of an existing scenario, with no source, and exactly `differential_instance_count` rows per scenario. `unresolved`: stays `UNRESOLVED`, carries no source, method, assertions or supporting references, states a missing-evidence reason and names no endpoint outside the catalogue. `revision_of`: a `SOURCE_STATED` scenario revision whose `REV:` digest is a `HISTORICAL_REVISION_OF` crosswalk row of that scenario (or of its fixture twin), is carried by the scenario's lineage where one is recorded, and cites the scenario's own repository. `pair_recorded`: its endpoint pair is already recorded by an embedded relationship of the same relation, with the same provenance and a matching type. An endpoint that is not in the catalogue is refused, never exempted. The manifest commits `relationship_row_accounting`: the row total, the count per class, the count per (type, provenance, relation_kind, method, confidence), the count per revision source and the number of placeholder relationships inside entries (`unresolved_accounting.unresolved_relationships`, a different population from the unresolved rows); the validator recomputes all of them [artifact_count_mismatch], so deleting or editing an unembedded row changes a committed count. Accepted limit: an attacker who rewrites the artifact, its digests and the manifest consistently and keeps every signature true is stopped only by the pinned manifest digest.

Denominators: `manifest.denominators` commits the ten separate denominators, the scenario classes, the differential instances (not scenarios) and the reason-code registries. Denominator 2 counts logical scenarios of release scope V0.1 and reports post-V0.1 ones apart; denominator 4 is three separate figures (specification cases, unexecuted other, adversarial) with no merged total; denominator 9 gives distinct (run, test node) pairs, distinct runs and runs with run results under their own names. The two registry labels (`runtime-authority-reasons/0.1` and `/0.2`) stay distinct entries; the report gives entries per label, entries resting on raw set B and distinct code names, and no combined figure.

## Loader contract

Input per partition `P` under `OUT/P/`: `P.canonical.json` (keys `rules`, `logical_scenarios`, `test_implementations`, `fixtures`; each an inline list or pointers `{file,count,sha256}` to shards `{entries:[...]}`), `P.crosswalk.json` (inline `rows` or `parts` pointers; catalogue dispositions in the forms `DISP`, `DISP:target`, `DISP(reason)` or with an explicit `target`; the normalizer forms `ATTACHED_TO:<id>`, `EVIDENCE_INDEXED:<digest>`, `SOURCE_REFERENCE_ONLY` are mapped only through the row's own statement (`disposition_legacy`, or `attach_kind`: parametrized_instance and collected_node to a test instance, byte_identical_location to ALIAS_OF, historical_revision and amendment_log_member to HISTORICAL_REVISION_OF); a form with no such statement is `UNRESOLVED` and reported), `P.evidence-index.json`. Optional overlays (`OUT/global/G1|G2|G3`): `{"overlay":"identity","merges":[{into,from,basis}]}`, `{"overlay":"attributes","items":{id:{normative_type,adoption_status,scenario_class,release_scope,mvp_applicability}}}`, `{"overlay":"relationships","items":[{owner,field,to,provenance,...}]}`. The loader guesses nothing: missing attributes become unknown or unresolved, links without provenance become `UNRESOLVED`, merges need a stated basis, a canonical id emitted by two partitions with different identity or different content refuses the load, shard pointers `{file,count,sha256}` are verified and confined to the partition directory, an evidence kind outside the exact source vocabulary is `unknown` (never a run result; a missing kind is classified only by structure: a run id plus a recorded outcome), and every defect is written to the load-problem list (partition, kind, ids, count; the manifest keeps counts, first ids and a digest over all ids). Partition totals are never summed before identity resolution.

## Limitations

Known and accepted. A reason code that a partition or a pass relabels `mandatory` (or the reverse), a classification, a scenario class and an applicability value are attributes the validator cannot verify against the source text; it can only require a stated basis and a recorded transition. Whether a cited quote, source location or `source_ref` says what is claimed is not mechanised. A schema that is weakened together with the manifest pins and the validator's own copy is outside the check; the manifest digest has to be pinned by a reviewer. The external artifacts are only checked when supplied. Evidence that records no source revision is carried as `unrecorded` and counted in the Catalogue Integrity Report (never as a stated source); `SOURCE_STATED` links refuse it.

The validator checks internal consistency, not the truth of source claims, the correctness of a tool run or the presence of source bytes. Raw record content is not read by the validator; only its digest commitments are. A passing validation is not a qualification, acceptance or release statement.
